# AI Assistant Context

**DigniFi** — trauma-informed bankruptcy filing platform (Chapter 7, ILND pilot district). Django REST API + React 19 frontend. Deployed on Heroku. Provides legal _information_, never _advice_ (UPL boundaries are non-negotiable).

## Quick Commands

```bash
docker compose up                              # Start all 3 services (db, backend, frontend)
docker compose exec backend python -m pytest --ds=config.settings.test -m "not slow"    # Fast backend run, about 2 min (sqlite :memory:, no postgres needed)
docker compose exec backend python -m pytest --ds=config.settings.test    # Full backend run, as CI runs it (CI adds --cov, which roughly doubles the time)
docker compose exec backend python manage.py migrate
docker compose exec backend python manage.py loaddata ilnd_2025_data   # Required before seed
docker compose exec backend python manage.py seed_demo_data            # Loads 6 AI personas

cd frontend && npm test                        # Frontend tests (vitest)
cd frontend && npm run e2e                     # E2E (requires backend running + seeded)
cd frontend && npm run lint:fix && npm run format
cd backend && ruff check . --fix               # Backend lint (pinned ruff==0.8.5)
```

## Gotchas (things agents get wrong)

- **DRF pagination** — list endpoints return `{count, results}`, not bare arrays. Always `Array.isArray` guard.
- **React 19 + navigate()** — calling `navigate()` in render body crashes the reconciler. Use `useEffect`.
- **Vite HMR in Docker** — type/structure changes don't hot-reload; restart the frontend container.
- **Enum mismatches are silent** — frontend/backend enum drift only surfaces at runtime; check both when adding fields.
- **Nested debts and assets save by id** — `IntakeSessionSerializer.update` upserts `debts`/`assets` through `_save_rows_by_id`: a row carrying one of this session's ids updates only the keys it sends, a row without one (or with an unknown or foreign id) is created on this session, and a stored row missing from the payload is **deleted**, so send every row you want to keep. A nested `session` is ignored. A session PATCH or PUT that carries `assets` or `debts` returns that list in the order it was sent, each row with its id (a new row, or one sent with a foreign or unknown id, shows its new id), so the wizard can pair rows by position and keep a new row's id; every other read of assets goes by id (`AssetInfo` has no `Meta.ordering`: `AssetViewSet` orders by `pk` and the session serializer sorts the nested list), and a session read lists debts by creditor name, ignoring case and accents, then id (`ordered_debts` in `apps/intake/claims.py`; `DebtInfo` has no `Meta.ordering` either, and `DebtViewSet` orders by `pk`) (DIG-164). A session PATCH that carries `expense_info` replies with the Expenses row it saved, and the reply's `legacy_payments` reads that row too (3c4 R17: before it, the reply held the copy read before the save). A nested debt row takes every answer the Amounts Owed step asks (3c3), a half-filled row included: a blank `creditor_name` or `debt_type` saves, `amount_owed` stays non-null: the server takes a number at or above 0, never a blank (the wizard sends a blank box as 0), and a negative is a 400 on every path. The row's address columns, `outside_us`, `date_incurred`, `home_payment_line`, `collateral_who`, `offset_answer`, `community_debt`, `lien`, `claim_status` and `notice_parties` save with it (`notice_parties` keep never-reused ids, at most 10 a debt), and `account_last_4` is read-only, the last four digits only. The five priority columns (`priority_answer`, `priority_other`, `priority_amount`, `nonpriority_amount`, `past_due_amount`, all encrypted and null until answered) save with a nested row and on the per-item path: an unknown `priority_answer`, a negative or too-wide figure and `priority_other` words past 100 characters are a 400, and a stored null reads as null. `secured_by` is an id or null: `_save_rows_by_id(…, scoped=…)` checks it against this session's assets, and an id that names no row of the session saves as no link and is never echoed. A removed property sets it null (`SET_NULL`). An asset row is a Schedule A/B row (3b): `ab_line` (a catalog key, or null on an old row, which round-trips), `details` (replaced whole on a save; a `kind` must be on that line, `percent` is stored as a string, and a figure sent with its `value_unknown`/`entire_unknown` flag clears the flag), `description`, `current_value` and `entire_value` (nullable, `min_value=0`, so $0 saves and comes back as `"0.00"`, and a value wider than `DecimalField(12, 2)` is a 400). `asset_type` is read-only, and `equity`, `account_number`, `financial_institution` and `amount_owed` are off the API (the `amount_owed` column stays one release). A session PATCH or PUT may also carry `asset_lines`, `{line: "yes"|"no"|null}`: it sets only the keys sent (null clears one), an unknown line or answer is a 400, and it locks the session and reopens a completed intake like any intake-data write. The Assets step saves the whole step (every row and every answer) each time. `POST /assets/` (the per-item path) refuses a row with no `ab_line`. The wizard holds the Assets, Amounts Owed, Contracts and Codebtors rows itself (`AssetsStep`, `DebtsStep`, `ContractsStep` and `CodebtorsStep` are controlled: `rows`, `onRowsChange`) and gives each row a browser-only `_key`, a loaded row's id or `new-<n>` from a counter in the step for a new row (not `crypto.randomUUID()`, which plain HTTP from another device lacks), which `saveCurrentStepData` leaves out of the request. After a save it writes the id at each position into the row with that `_key`, wherever it now sits, skips a row removed while the save was on its way, and takes nothing else from the reply, so amounts stay as typed. Only the newest save of a list writes ids: a reply that lands after a later save of the list has gone out (an autosave, or Continue, on a slow link) changes nothing, since the later save left without this reply's ids and the server has already replaced any row the earlier save created, so a save that went out after an earlier reply never carries an id that reply replaced. One case is not covered: a session PATCH or a list PUT that fails and is retried by `withRetry` (`api/client.ts`) can land on the server after a newer save (Continue during the retry's 0.5–3.5 s backoff), so the server keeps the older save's values and the browser can hold an id the server deleted. A reply whose list is a different length from the one sent fails the save rather than pairing ids by guesswork. Fields the browser never receives (`account_number`, `source_document`) survive a re-save. `DebtViewSet`/`AssetViewSet` keep the base serializers, so per-item create never takes a client id, and a debt's `secured_by` and a contract's or codebtor's links are read-only on the per-item paths. Contracts and codebtors save the same way, as a whole list: `PUT /intake/sessions/{id}/contracts/` (or `codebtors/`) locks the session, then checks every row before writing any, and replies with the rows in the order sent, each with its id; an empty list deletes every stored row, and a GET lists them by id. A contract row also takes its address, `outside_us`, `lease_kind`, `monthly_payment`, `vehicle_asset`, `owes_now` and `owed_debt`, and a codebtor row its `street_2`, `outside_us` and `links` (`[{kind, id}]`, dropped on read when the row is gone); a name or a type may be blank, and a link to another filer's row saves as no link. The wizard holds both lists with a `_key` (`ContractRow`, `CodebtorRow`), sends each step's list by autosave while the step can continue and on Continue, pairs the reply's ids by position under `listSavesRef.contracts`/`codebtors` as for assets, and reads both with the session before any step shows, so a list that failed to load is never saved as empty. A new row with nothing in it stays out of the PUT, and any other row goes, even with no name: a stored row whose name is cleared is sent nameless under its id, so it is kept and Complete names it (R17). Review lists the rows with an id. The Income step's household rows are held by the wizard the same way, as `householdRows` with a `_key`. They pair ids under `listSavesRef.members`, and only the newest save writes them. The Income step's business and rental entries are held the same way, as `entryRows`/`spouseEntryRows`, and pair under `listSavesRef.entries`/`spouseEntries`. One session reply pairs every list it carries: members, entries and the spouse's entries. The server's rules for those rows differ: see "The household list".
- **Saves lock the session** — every write to a session's intake data first calls `lock_session` (`apps/intake/locking.py`, `select_for_update` on the session row) inside the same `transaction.atomic()` block as the write, so a second save of the same session waits for the first to commit and then reads what it stored (DIG-188). That covers the session PATCH and PUT, `update_step`, `complete` (which writes only `status` and `completed_at`), the contracts and codebtors PUT, POST and DELETE, the filing-fee PUT (`PUT /intake/sessions/{id}/filing-fee/`, which never reopens), the exemptions PUT (`PUT /intake/sessions/{id}/exemptions/`, which validates before it locks and never reopens), the `DebtViewSet`/`AssetViewSet` writes, a scanned bill's correction and an upload's findings. Call `get_object()` before locking (another user's session is a 404), and lock before reading anything the write depends on. An upload locks only in its worker thread, around the write of its findings, after the call to the hosted model: the upload request waits for that thread, so a lock taken in the request deadlocks. `select_for_update` does nothing on sqlite, so the backend suite can't see a missing lock; only `apps/intake/tests/test_session_lock.py` (marker `postgres`) proves it, and it skips under the default settings. Run it locally with `DJANGO_SETTINGS_MODULE=config.settings.test_postgres pytest -m postgres`, with `DATABASE_URL` naming a Postgres whose user can create the test database; CI runs it in the backend job against its Postgres service. `test_postgres` sets a 10-second `lock_timeout`, so a deadlock fails a test instead of hanging the run. The session PATCH's lock covers its `household`, `spouse_income`, `income_info` and `asset_lines` keys, and the lock test's `WRITES` holds the household, income, `asset_lines`, `claim_answers`, `petition_answers` and `schedule_i_answers` PATCHes (none of these session-PATCH rows fails without `lock_session`, since every session PATCH writes the session row anyway; the lock in `IntakeSessionViewSet.update` does the real work), the debts PATCH with links, Continue to step 7 (which confirms drafts under the lock), the filing-fee PUT and the exemptions PUT. `AssetViewSet.update` locks before it validates, since validating reads the stored row's `details`: the row's session and, for a move, the filer's other session, in id order.
- **Debt and asset amounts are readable, as strings** — the owner gets `DebtInfo.amount_owed`, `DebtInfo.monthly_payment` (or null) and `AssetInfo.current_value` and `entire_value` back, and the three priority figures `priority_amount`, `nonpriority_amount` and `past_due_amount` too (decimal strings or null, hydrated through `DEBT_AMOUNT_FIELDS` in `IntakeWizard.tsx`, bounded by `DebtInfoSerializer`) (the SSN and a debt's `account_number` stay write-only; an asset's `account_number` and `amount_owed` are off the API). DRF sends decimals as strings (`"2500.00"`) and an asset's unanswered value as null, so the wizard converts them with `hydrateAmounts` (`utils/parseAmount.ts`) as session data enters step state, a null becoming `undefined`; a raw string in a step's `reduce` joins as text (`$02500.00100.50`). A stored amount wider than `DecimalField(12, 2)` makes every read of that session 500, so every write path must bound it (`DraftDebtCreator` stores it as 0; documents `validate` returns 400; `AssetInfoSerializer` returns 400). A debt's `account_number` stays write-only: the reply carries `account_last_4`, its last four digits and no other. A negative `amount_owed` is a 400 on the session save, the per-item save and a scanned bill's correction.

- **The household list** — `Household` is one-to-one with the session. Its `county` is encrypted and must be one of `ILND_COUNTIES`, or it is a 400. Its `members` are encrypted JSON: null means unanswered, and `[]` means the filer said no one. Step 1 sends `{household: {county}}` and step 2 sends `{household: {members}}`; the serializer updates only the keys sent. Ids come from `next_member_id` and are never reused: a row sent with one of the list's ids replaces the stored row whole, a row with no id, an unknown id or a repeated one gets a new id, and the reply lists the rows in the order sent, each with its id. One row shape: `id, relationship, age, lives_with_you, claimed_or_supported`, then `spouse_is_dependent` on the spouse's row only, with null for an unanswered question; `HouseholdSerializer.to_representation` returns the stored rows as they are. No names are stored. A 400 is only for a value no answer can have: an unknown relationship, an age outside 0–120 or not whole, a second spouse row, `spouse_is_dependent` on another row, or a 21st row. A missing answer saves, and Complete names it. `household.family_size` and `household.fee_waiver_household_size` are read-only, and null while `income_step_gaps` finds a gap. Two backend tests pin the frontend's copies of the server's words: `test_household_frontend_copy.py` pins `RELATIONSHIP_WORDS` to `frontend/src/constants/household.ts` and `ILND_COUNTIES` to `counties.ts`. The forms' own words (line 1, its declaration, the glossary sentence) live in `formText.ts`, which no reading-level test scores. DigniFi's own sentences go in `copy.ts`.

- **user-event hangs under vitest fake timers** — RTL's `asyncWrapper` drains every user-event action with a `setTimeout(0)` that only a `jest` global advances, so `userEvent.setup({ advanceTimers })` doesn't help. Under `vi.useFakeTimers()` use `fireEvent` + `act(() => vi.advanceTimersByTimeAsync(ms))`, step the clock in ≤1 s increments when each timer's reply schedules the next one, and switch back to real timers before any `userEvent` action, `findBy` or `waitFor`.

## Architecture (quick)

- **Backend:** Django 5.0 + DRF, Python 3.11, PostgreSQL 15, `encrypted-model-fields` (Fernet PII encryption)
- **Frontend:** React 19 + Vite 7 + TypeScript, Context API (not Redux), react-router-dom v7
- **PDF:** pypdf and PyMuPDF draw on the official AO court templates. Each schema in `data/forms/schemas/` binds a field to a widget's full name in the field index (`data/forms/field_index/<template stem>.index.json`). `build_parts(form_type, session)`, which the views call, checks the form's preconditions and resolves its schema into the parts document `field_values` stores (`build_field_values` returns the form's `{key: value}` instead); `PDFFormFiller().check(form_type, values)` plans the widgets each key names (a full name, or `<full name>@<page>:<tag>` for one widget) in the template from `data/forms/pdfs/`, and raises `UnknownField` for any other name; `fill()` runs it, then pypdf builds each planned widget's own appearance (`_paint_background` adds the box's own `/MK /BG` under its text, as a viewer would: the 18 district boxes that sit on the page's printed "District of" (two on 103B, one on each of 16 other forms; Form 101 (11/26) names its court in two text boxes with none) and 15 of Schedule C's boxes have one, and it is all that hides those words and the ruled lines under Schedule C's; the other text boxes have none and stay see-through; `test_box_background.py` judges this by pixels, since a text read-back can't see one) and PyMuPDF bakes every remaining widget into the page (every push button, Print, Reset, Save As and Add Attachment, and the second widget of each stacked pair are removed first), so the PDF it returns can't be filled in a viewer.
- **PDF templates:** 69 official AO court PDFs in `data/forms/pdfs/` (committed; Form 101 is `form_b101.pdf`, the 11/26 revision, and its index is hand-adjudicated by `tools/build_form_101_index.py`, no vision run). Baked into Heroku image.
- **Forms:** 19 form types in `apps/forms/registry.py` (`FORM_REGISTRY` / `get_all_form_types()` / `packet(session)`). `generate_all` gives each form its own savepoint.
- **OCR service:** provider-agnostic. `OCR_PROVIDER` selects `openai` (default, `gpt-4o`, `OPENAI_API_KEY`) or `gemini` (`gemini-2.0-flash`, `GEMINI_API_KEY`); `OCR_MODEL` overrides the model so a model change is a config var, not a deploy. No local model — both call a hosted API directly.
- **Auth:** JWT (simplejwt). Access in memory, refresh in localStorage. `POST /api/token/obtain/` + `/api/token/refresh/`.
- **E2E:** 6 AI persona briefs in `docs/testing/persona-briefs/` (andres, deshawn, james, maria, priya, sarah) driving 9 journey specs — one per persona plus `sofa-journey.spec.ts`, `scanned-bill-journey.spec.ts` (an upload read through a fake OpenAI server) and `eviction-statement-journey.spec.ts` (a renter with an eviction judgment, Form 101A). `seed_demo_data` creates synthetic sessions with all intake data.
