# AI Assistant Context

**DigniFi** — trauma-informed bankruptcy filing platform (Chapter 7, ILND pilot district). Django REST API + React 19 frontend. Deployed on Heroku. Provides legal _information_, never _advice_ (UPL boundaries are non-negotiable).

## Quick Commands

```bash
docker compose up                              # Start all 3 services (db, backend, frontend)
docker compose exec backend python -m pytest --ds=config.settings.test    # Backend tests (sqlite :memory:, no postgres needed)
docker compose exec backend python manage.py migrate
docker compose exec backend python manage.py loaddata ilnd_2025_data   # Required before seed
docker compose exec backend python manage.py seed_demo_data            # Loads 6 AI personas

cd frontend && npm test                        # Frontend tests (vitest)
cd frontend && npm run e2e                     # E2E (requires backend running + seeded)
cd frontend && npm run lint:fix && npm run format
cd backend && ruff check . --fix               # Backend lint (pinned ruff==0.8.5)
```

## Gotchas (things agents get wrong)

- **DRF pagination** — list endpoints return `{count, results}`, not bare arrays. Always `Array.isArray` guard.
- **React 19 + navigate()** — calling `navigate()` in render body crashes the reconciler. Use `useEffect`.
- **Vite HMR in Docker** — type/structure changes don't hot-reload; restart the frontend container.
- **Enum mismatches are silent** — frontend/backend enum drift only surfaces at runtime; check both when adding fields.
- **Nested debts and assets save by id** — `IntakeSessionSerializer.update` upserts `debts`/`assets` through `_save_rows_by_id`: a row carrying one of this session's ids updates only the keys it sends, a row without one (or with an unknown or foreign id) is created on this session, and a stored row missing from the payload is **deleted**, so send every row you want to keep. A nested `session` is ignored. A session PATCH or PUT that carries `assets` or `debts` returns that list in the order it was sent, each row with its id (a new row, or one sent with a foreign or unknown id, shows its new id), so the wizard can pair rows by position and keep a new row's id; every other read keeps model order (DIG-164). The wizard holds the Assets and Amounts Owed rows itself (`AssetsStep`/`DebtsStep` are controlled: `rows`, `onRowsChange`) and gives each row a browser-only `_key`, a loaded row's id or `new-<n>` from a counter in the step for a new row (not `crypto.randomUUID()`, which plain HTTP from another device lacks), which `saveCurrentStepData` leaves out of the request. After a save it writes the id at each position into the row with that `_key`, wherever it now sits, skips a row removed while the save was on its way, and takes nothing else from the reply, so amounts stay as typed. Only the newest save of a list writes ids: a reply that lands after a later save of the list has gone out (an autosave, or Continue, on a slow link) changes nothing, since the later save left without this reply's ids and the server has already replaced any row the earlier save created, so a save that went out after an earlier reply never carries an id that reply replaced. One case is not covered: a session PATCH that fails and is retried by `withRetry` (`api/client.ts`) can land on the server after a newer save (Continue during the retry's 0.5–3.5 s backoff), so the server keeps the older save's values and the browser can hold an id the server deleted. A reply whose list is a different length from the one sent fails the save rather than pairing ids by guesswork. Fields the browser never receives (`account_number`, `source_document`) survive a re-save. `DebtViewSet`/`AssetViewSet` keep the base serializers, so per-item create never takes a client id. Contracts and codebtors save the same way, as a whole list: `PUT /intake/sessions/{id}/contracts/` (or `codebtors/`) checks every row before writing any, and an empty list deletes every stored row. The wizard sends each list on Continue from steps 6 and 7, and reads both with the session before any step shows, so a list that failed to load is never saved as empty.
- **Saves lock the session** — every write to a session's intake data first calls `lock_session` (`apps/intake/locking.py`, `select_for_update` on the session row) inside the same `transaction.atomic()` block as the write, so a second save of the same session waits for the first to commit and then reads what it stored (DIG-188). That covers the session PATCH and PUT, `update_step`, `complete` (which writes only `status` and `completed_at`), the contracts and codebtors PUT, POST and DELETE, the `DebtViewSet`/`AssetViewSet` writes, a scanned bill's correction and an upload's findings. Call `get_object()` before locking (another user's session is a 404), and lock before reading anything the write depends on. An upload locks only in its worker thread, around the write of its findings, after the call to the hosted model: the upload request waits for that thread, so a lock taken in the request deadlocks. `select_for_update` does nothing on sqlite, so the backend suite can't see a missing lock; only `apps/intake/tests/test_session_lock.py` (marker `postgres`) proves it, and it skips under the default settings. Run it locally with `DJANGO_SETTINGS_MODULE=config.settings.test_postgres pytest -m postgres`, with `DATABASE_URL` naming a Postgres whose user can create the test database; CI runs it in the backend job against its Postgres service. `test_postgres` sets a 10-second `lock_timeout`, so a deadlock fails a test instead of hanging the run.
- **Debt and asset amounts are readable, as strings** — the owner gets `DebtInfo.amount_owed` and `AssetInfo.current_value`/`amount_owed` back (SSN and `account_number` stay write-only). DRF sends decimals as strings (`"2500.00"`), so the wizard converts them with `hydrateAmounts` (`utils/parseAmount.ts`) as session data enters step state; a raw string in a step's `reduce` joins as text (`$02500.00100.50`). A stored amount wider than `DecimalField(12, 2)` makes every read of that session 500, so every write path must bound it (`DraftDebtCreator` stores it as 0; documents `validate` returns 400).
- **Seed order** — `seed_demo_data` requires `loaddata ilnd_2025_data` first, or means test has no median income data. It reads the median table in force on today's real date, not the tests' pinned one, and when none is (from November 1, 2026 until the November table is loaded) it prints a message naming `docs/REFERENCE_TABLES.md` and changes nothing, so even `--reset` leaves the existing personas. Personas seeded before income was stored by source must be re-created with `seed_demo_data --reset` (migration 0014 leaves their totals unsplit, and a plain re-run skips existing users).
- **household_size defaults to 1** — `DebtorInfo.household_size` has `default=1`; the means test prefers it over deriving from marital status + dependents. Always set it explicitly.
- **The packet decides which forms a filer gets** — `apps/forms/registry.py` maps each form to `applies(session)` and `requires(session)`. 103B applies only with a `FeeWaiverApplication`; 122A-2 only when `MeansTest.calculated_cmi × 12 > median_income_threshold`, through `is_above_median` (`apps/eligibility/cmi.py`), the means test's own comparison, so income exactly at the median counts as below (DIG-136). Never read `above_median_calculated`: a row calculated before DIG-128 was fixed can still carry a stale True. 122A-1Supp not until step 4; 122B is gone. A packet holds 14–16 forms. Generate All, Generate, Regenerate, the download of an unfiled form and the packet list of a completed intake work the means test out again from the stored intake first (`_recalculate_means_test` in `apps/forms/views.py`), so a stale `MeansTest` row never decides the packet (DIG-160); an unfinished intake's packet list reads the stored row. `generate` on a form outside the packet, or with a missing precondition (`PreconditionMissing`), is a 422 in plain words, and so are income not entered by source (`IncomeNotSplit`) and no median table in force on the fill date (`NoTableInForce`, which logs the table, the date and the district); any other failure is a 500 logged by exception type only.
- **Forms need a completed intake** — through the API, only the session's `complete` action sets `status="completed"`: `status` and `current_step` are read-only on `IntakeSessionSerializer`, and `update_step` takes only a whole number from 1 to 8 (anything else is a 400). Complete refuses with a 400 `{message, errors: [{step, message}]}`, one entry per gap in wizard order, each `step` a `WIZARD_STEPS` key: no `DebtorInfo` row (the name-and-address sentence; the fields themselves aren't checked) or an SSN that isn't 9 digits (the registry's own `_needs_ssn`, so Complete and Forms 101 and 121 say the same thing), income not entered by source (`IncomeNotSplit`, no income row included), an Expenses step never saved (no `ExpenseInfo` row), and a scanned debt the filer hasn't confirmed (a `DebtInfo` with `is_draft`, step `debts`; see "Document upload sits mid-wizard"). The forms views refuse any other status with a 422, "Finish your intake before preparing your forms.": Generate All once for the whole call, before it deletes anything; Generate, Regenerate and the download of an unfiled form through `_prepare`. The packet list never refuses an unfinished intake. A forms refusal also carries the `step` (a wizard step key) or `page` (a route) that fixes it, when the exception names one: `PreconditionMissing.step`, `IncomeNotSplit.step` (`income_info`) and `IntakeNotFinished.page` (`/intake`); "already filed", "not in your packet" and `NoTableInForce` carry neither, and the key is absent, never null. The check lives in the views, not in `build_field_values`, so forms view tests need a completed session, with income by source and a district with a median table in force on the fill date, since Generate All, Generate, Regenerate, an unfiled download and a completed intake's packet list work the means test out. Every intake-data write sets a completed session back to `in_progress` through `IntakeSession.reopen()`, so the filer presses Complete again: a session PATCH carrying `debtor_info`, `income_info`, `expense_info`, `debts` or `assets`; the contracts and codebtors endpoints; `DebtViewSet`/`AssetViewSet` writes; an upload that adds a draft debt or pay-stub figures, and a correction to a scanned bill or pay stub. `update_step` (Continue) sets `in_progress` itself. Form answers (`answers/bulk`), SOFA and the fee-waiver application never reopen it; a new intake-data write path must lock the session first (see "Saves lock the session") and call `reopen()`. A failed Complete or means-test call keeps the filer on Review (DIG-150), and the dashboard shows a "Finish your intake" link back to the wizard until the session is complete.
- **SSN on forms** — Form 101's `Debtor1.SSNum` gets the last 4 digits from the `ssn_last_4` derivation; the full SSN appears only on Form 121.
- **Means test units** — CMI is monthly, Census median is annual. `MeansTest.calculate()` annualizes CMI ×12 per § 707(b)(7). The original bug passed everyone.
- **Dated tables and the fill date** — `in_force(rows, on, table, district)` (`apps/districts/dated_tables.py`) takes the newest row whose `effective_date` is on or before `on` (later rows are ignored) and returns it unless its `valid_through` is set and earlier than `on`; when that row has expired, or no row has started yet, it logs one line (the table, the date and the district) and raises `NoTableInForce`, a `ValueError` carrying the filer's sentence, and never looks at an older row. Every lookup of a dated table takes `fill_date()`, the day the forms are filled in America/Chicago, which stands in for the filing date. The root `backend/conftest.py` pins `_today` to 2026-10-16 for every backend test, so a test of a lookup sets its own day with `monkeypatch.setattr("apps.districts.dated_tables._today", ...)`, and no module may import `_today` by name. A scheduled row (`DatedTable`: `effective_date`, `valid_through`, `source_url`) carries `valid_through`, the day before its next scheduled change, and an empty one means open-ended; a test fails on a fixture median row without one. The dev server, the seed and E2E use the real date, so from November 1, 2026 every forms call, the means test, `seed_demo_data` and CI's E2E job refuse until the November median table is loaded. `docs/REFERENCE_TABLES.md` says where each table is posted and how to add a row.
- **GenerateAll vs single** — `/generate_all` returns `{generated, errors}`; single returns `{form, message}`. A refusal of the whole call is `{error}` with no `form_type` (plus its `step` or `page`, as in "Forms need a completed intake"): Generate All for an unfinished intake (422), and Generate All or a completed intake's packet list for income not entered by source or no median table in force on the fill date (both 422). `generate_all` covers only the packet and deletes the rows of unfiled forms that no longer apply. A form marked filed keeps its stored answers, even after it leaves the packet (DIG-155): `generate_all` leaves it untouched and returns it in `generated`, in its packet position, or after the packet's forms once it has left the packet; its download fills from its stored `field_values` without the packet check; `generate` and `regenerate` return 422 for it, but only after the completion check and the means test, whose refusal comes first. `GET /api/forms/packet/?session=<id>` returns `{session, form_types, tables}` in filing order, `tables` being the median table the means test used (empty with no means test, or one stored before `calculation_details["median_table"]` existed) and the source of the dashboard's notice naming it; the dashboard renders from it, reloads it after every Generate All, and shows a filed form outside it as "Filed, no longer in your current packet".
- **Schemas are checked at startup** — `apps/forms/checks.py` validates all 17 schemas against the field index (forms.E001–E007: missing schema or index, template hash, full names, widget types and choices, export states and `/Opt` values, duplicate bindings, TBD sources and unknown rules, predicates, namespaces or repeat capacity). `manage.py check`, `runserver` and `migrate` (so the Heroku release) fail on a bad schema; pytest runs no system checks, `test_checks.py` does. A binding with a `tag` names one widget of its full name, the one with that index tag on its `page` (`apps/forms/services/widgets.py` matches each template widget to its index row), and resolves under the key `<full name>@<page>:<tag>`, which `fill()` doesn't take yet: E003 refuses a tag that isn't a widget of that name on that page, or names one that never prints a value (a print button, or the second of one of Schedule D's stacked pairs), and E006 counts the widgets each binding would fill, so a tagged and an untagged binding of one name conflict. E003 also refuses an index full name containing `@`, which marks a widget's own key. A checkbox or radio binding carries `choices` (answer → export state): `{"true": state}` is one box. Any other map takes only its own keys: a rule or answer feeding it must return one of them or `""` (blank), and any other value raises `UnmappedChoice`, a 422 in plain words. `{}` prints nothing, and tier 1's `test_every_checkbox_binding_maps_its_answers_to_a_box` fails on it.
- **Known form defects are strict xfails** — `backend/apps/forms/tests/known_defects.json` lists every oracle case (tiers 1–3) that fails, each with its DIG ticket. It has been empty (`[]`) since forms step 2b: every oracle case passes, and the one xfail pytest still reports is a marker in `apps/intake/tests/test_integration_flow.py`, outside the list. Fixing a defect turns its xfail into a failure until you delete the entry. A tier 2 case is keyed on its box and its binding key, `<source>:<producer>` (for example `derived:schedule_j_vehicle_payment`), so re-ruling or moving a listed binding orphans its entry, and the orphan test fails until you delete it; tier 2 also pins how many cases it asserts (`ASSERTED_CASES` in `test_oracle_tier2.py`), so a binding change that alters coverage updates that number on purpose. Delete cleared entries by hand, not by running the recorder (`data/forms/field_index/tools/record_known_defects.py`, usage in its docstring): a green suite proves the list exact, since a listed case that passes is a strict XPASS and an entry with no case behind it fails the orphan test. Deleting by hand also keeps the recorder's missing tickets for five forms (DIG-143) out of the list.
- **A new placement needs its addendum row in the same commit** — tier 2 asserts a binding only where a checked row covers its box and key. A binding the audit never judged (step 2's ADD rows) needs a row in `data/forms/field_index/audit/step2_verification.json`, committed with the binding: `verification.json`'s shape plus `producer`, spelled as the whole binding key (`derived:phone`, `constant:yes`), its evidence citing the box's field-index label and any owner answer that decided it. Tier 2 joins it on (box, key) before the audit rows, and `test_every_step2_placement_matches_a_binding` fails on a row no binding matches. A binding moved onto the box an audit row names needs no row: the moved-here join asserts it.
- **Blank, not 0.00, on the forms** — a derivation must not turn a missing input into 0.00: a line DigniFi never asks (interest, payroll deductions, priority, a spouse's column) and an income source left empty print blank, and a source typed as $0 prints 0.00. A total counts an unasked line as zero and still prints. The 13 expense amounts are stored as $0 when left empty, so an expense line (Schedule J, 122A-2 lines 19 and 21) prints only above $0, while the totals (Schedule J 22a and 22c, 106Sum line 5, 103B line 6) still print. One exception remains: with no `ExpenseInfo` row at all, those totals and Schedule J 23b print 0.00, and 23c prints the income less 0.00 (`_total_monthly_expenses`, the one function behind all of them; any other error fails the form). Signature lines and signing dates stay blank for wet ink (`test_signing_lines.py`). No production schema has a repeat group: Form 107's prior-income and creditor-payment rows came off until steps 3–4 ask what they need, and the SOFA answers stay stored. The engine (`repeat`, `RepeatOverflow` and its 422) stays for later steps; only synthetic tests reach it.
- **`field_values`, not `form_data`** — `GeneratedForm.field_values` holds the resolved values as encrypted JSON, and the API never returns it. `form_data` is blank; its column is dropped one release after this code is live. A filed form downloads its stored `field_values`; an unfiled one is resolved fresh on every download.
- **Analytics auth** — `trackEvent()` must use `getAccessToken()` for Bearer header, not raw fetch.
- **heroku.yml release** — must be one command string (not argv list). `heroku releases:output` is empty; use `heroku logs --dyno release`.
- **CI ruff is pinned** — `ci.yml` installs `ruff==0.8.5`. Unpinned ruff broke CI when new rules shipped.
- **Branches: develop → main → prod** — `develop`, `main` and `prod` are the three long-lived branches. Every feature PR targets `develop` (`gh pr create --base develop`) and is squash-merged. When a body of work is finished, `develop` is promoted to `main` by a fast-forward push; `main` is the stable copy for people who run DigniFi on their own machine and stays the GitHub default branch. `prod` is what Heroku runs: a deploy fast-forwards `prod` to `main`, then runs `git push heroku prod:main` (not `git push heroku main`, which older plans show), and only the owner deploys. Promotions are fast-forward pushes, never PRs: the repo disallows merge commits, and squash or rebase merges would give the branches different commits. CI runs on pushes and PRs for all three branches, and a ruleset blocks deletion and force-push on all three.
- **opendataloader-pdf needs a JRE** — both Dockerfiles install `default-jre-headless`. Without one, every PDF falls back to vision. `TestRealJvmContract` (`apps/documents/tests/test_processor.py`) runs the real CLI wherever `java` is on PATH and skips with a visible reason elsewhere (`-rs` in CI); every other test uses a stand-in for the module.
- **No PDF sidecar** — the `odl-hybrid` service and the `opendataloader-pdf[hybrid]` extra are gone; the backend runs the Java CLI itself. A stack or venv built before the removal still has them: run `docker compose up --build --remove-orphans` and recreate `backend/.venv` (`pip install -r` never uninstalls docling or torch).
- **Pre-commit prettier** — reformats staged files on first commit; re-`git add` and commit again.
- **Colima volume mounts** — Colima only mounts `$HOME` by default; `/Volumes/Containers` must be added in `~/.colima/default/colima.yaml`.
- **Compose backend** — command must chain `python manage.py migrate && ...` before `runserver`.
- **Frontend tests use MSW** — network requests are intercepted in `src/test/setup.ts`. Write MSW handlers for new API calls.
- **E2E needs full stack** — Playwright tests (`frontend/e2e/journeys/`) require backend running, migrations applied, and `seed_demo_data` loaded. `scanned-bill-journey` also needs `OPENAI_BASE_URL=http://127.0.0.1:4010/v1` in both the backend's and Playwright's environment, plus `OCR_PROVIDER=openai` and a dummy `OPENAI_API_KEY` for the backend; the spec starts the fake OpenAI server itself (`e2e/fixtures/fake-openai.ts`). Without the wiring it skips locally (printing why) and fails in CI. Export the dummy key: exported variables beat the repo-root `.env`, which may hold a real one.
- **`OPENAI_BASE_URL` comes from the SDK, not settings** — `OpenAIProvider` passes only the key; the `openai` SDK reads `OPENAI_BASE_URL` from the environment itself. An empty value (`OPENAI_BASE_URL=` in `.env`) is not ignored: the SDK uses `''` as the base URL and every OCR call fails.
- **Backend test settings** — `DJANGO_SETTINGS_MODULE=config.settings.test` uses sqlite `:memory:`, no postgres. E2E tests use `config.settings.development` (needs postgres).
- **FIELD_ENCRYPTION_KEY** — must be a real Fernet key (32 url-safe base64 bytes). CI uses `U9HKckkKBeT8wag2jMcOx2Cez2M2jtvNG4qxSHuYcAo=` (synthetic, encrypts nothing).
- **UPL compliance** — all user-facing text must be information, never advice. See `docs/UPL_COMPLIANCE.md`.
- **Nested `CLAUDE.md` files are empty stubs** — they are auto-generated `claude-mem` placeholders (~170 bytes each) reading `*No recent activity*`. This root file is the only real one; don't go looking for per-app conventions in them.
- **OCR provider is config-driven** — `_get_processor()` branches on `settings.OCR_PROVIDER` (`openai` | `gemini`) and lazy-imports the provider, so a missing SDK/key surfaces at OCR time, not app boot. `OCR_MODEL` empty ⇒ the provider's own default. Don't hardcode a provider.
- **`openai_provider.py`, never `openai.py`** — a module named `openai.py` inside `providers/` would shadow the installed `openai` package.
- **Prod throttling lives in `production.py`, not `base.py`** — base defines only the `auth` scope (`30/minute`); production adds `DEFAULT_THROTTLE_CLASSES` with `anon: 60/minute`, `user: 120/minute`, `auth: 5/minute`. Reading base alone wrongly concludes endpoints are unthrottled — polling ~14 documents exhausts `user` fast.
- **Document upload sits mid-wizard** — the flow is `login → /intake` step 1 → `/documents` → `/intake` steps 2–8. A scanned bill or credit report pre-fills Amounts Owed; a pay stub supplies only Schedule I's employer name (`IngestedAggregate` `paystub.employer_name`), never an amount and never the Income step: every income box prints what was typed on the Income step. A scanned debt is a draft (`is_draft`) and stays off every form and out of the means test until the filer saves the Amounts Owed step, whose session PATCH carrying `debts` clears every draft of the session; Complete refuses while one remains (DIG-163). Every reader that feeds a form or the means test reads through `DebtInfo.objects.confirmed()` or `session.debts.confirmed()`, and a new one must too; dischargeability, the completion percentage and the API's reads still see drafts, so the wizard can show them. The aggregator still stores `paystub.gross`, which no form reads (pre-fill is DIG-176). `IntakeWizard.handleNext` detours when `nextStep === 2`. Nothing currently links back to `/documents` after a skip. The persona journeys pass the detour with `DocumentsPage.skip()` (`e2e/pages/documents.page.ts`) after step 1; `scanned-bill-journey` uploads with `uploadBill()` and clicks Continue.
- **`updateCurrentStep` is POST `/intake/sessions/{id}/update_step/`** — _not_ the PATCH that saves step data. Mocking the PATCH to assert step advancement silently captures the wrong call and passes vacuously.
- **Upload is synchronous despite the 202** — `views.py` uses `with ThreadPoolExecutor(...)`, whose `__exit__` calls `shutdown(wait=True)`, so `{"status": "processing"}` is returned _after_ OCR completes and holds a gunicorn worker. No `Future` is retained — that's the tell.
- **PDFs: text layer first, then up to 3 scanned pages** — `processor.py` runs `opendataloader_pdf.convert(..., format="markdown", image_output="off", include_header_footer=True)` with no hybrid arguments. Text of at least `_MIN_TEXT_LENGTH` (30) characters goes to the text prompt; otherwise `_pdf_to_page_images()` sends up to `_MAX_SCANNED_PAGES` (3) JPEG pages to vision, and a PDF with no pages fails. Without `image_output="off"` a scan's image placeholders reach the text prompt; without `include_header_footer=True` the letterhead naming the creditor is dropped.
- **`extract()` takes a list of page images** — `BaseOCRProvider.extract(images: list[bytes], prompt)`: `[]` means text mode, a photo upload is a one-item list, and pages go in page order (one OpenAI `image_url` part or one Gemini inline part each). `classify()` still takes bytes. Never hand a provider `[]` for a scan.
- **An empty OpenAI reply raises `EmptyModelReply`** — `OpenAIProvider._complete` retries a blank or whitespace-only reply once, but never a refusal or `finish_reason == "content_filter"`. The error names `finish_reason` and whether a refusal was present, never its text. `_parse_result` records only the reply's length ("model reply was not valid JSON (N characters)"), so `error_message` never holds model output. Gemini still returns `""` (DIG-35).
- **The wizard re-reads the session on every mount** — `IntakeWizard` fixes the session id at mount (context session, else `current_session_id`), calls `loadSession(id)`, and renders no step until it returns, so steps and autosave start from server data, not the context copy (which predates any upload on `/documents`). A failed read shows a "Try again" alert for the same id; a 404 starts a new session. `loadSession`/`createSession` resolve with the session, and `loadSession` clears `current_session_id` only on a 404, but the provider's own startup load still clears it on any error (DIG-11).
- **Autosave sends only real edits** — `useAutoSave` compares the step's PATCH body (`currentStepBody` in `IntakeWizard`) as JSON with that step's last saved or loaded copy (the first body seen under a step's name) and skips an equal one, so showing a step again (Go Back) sends nothing and doesn't reopen a completed intake. A body must therefore be built the same way from loaded data as from edited data: leave out read-only totals and echoed fields, or every visit saves. A save of assets or debts returns the copy the server now holds, the sent rows with the ids the reply gave them, built by the same merge as the wizard's rows, unless a later save of the list has gone out since (it then returns nothing); `onSave` may return such a copy, and the hook keeps it as the saved copy, so the ids reaching the rows send nothing more. Continue (`saveNow`) always saves. Steps 6 and 7 have no body there; their lists save only on Continue.
- **An empty scan is FAILED, not done** — `documents/views._record_findings` judges each type: a bill needs a creditor name, a pay stub must pass `PayStubExtraction`, the check the income aggregate applies (gross pay + both pay-period dates required; an invalid optional field such as a negative `net_pay` also fails it), a credit report needs one readable tradeline. Otherwise `OCRResult.status="failed"`, `failure_reason="nothing_found"`; any exception is `processing_error`. A bill with a creditor but no readable balance is `completed` with a $0 draft; a report of only $0 accounts is `completed` with no debts. Other document types are not judged.
- **The documents API never returns `error_message` or `extracted_data`** — `_serialize_ocr` returns `status`, `failure_reason`, `confidence_scores`, `overall_confidence`, `user_validated`. `error_message` is operations-only (exception class, `finish_reason`); read it in a Django shell. The pipeline's catch-all handlers (`_run_processing`, `AggregateIngestionService.recalculate`) log only the exception's type with `logger.error`, never `logger.exception`: logs reach Sentry, and a DB error's DETAIL quotes row values (DIG-105).
- **Scanned amounts are bounded** — `draft_debt._bounded_amount` stores a non-numeric, negative, non-finite or ≥1e10 balance as 0, and `TradelineItem.amount_owed` has `le=9999999999.99`: a wider value makes `DecimalField(12,2)` raise on every read of the session.
- **Prompt hints are per type and shared** — `_FIELD_HINTS` in `documents/services/providers/prompts/image_extraction.py` feeds both the vision and the text prompt (`text_extraction.py` imports it). A type with no hint is asked for "all visible fields as key-value pairs" and never returns the keys its importer reads; the `CREDIT_REPORT` hint's keys must stay in step with `TradelineItem`, and `test_prompts.py` checks that they do.
- **Income is stored by source** — `IncomeInfo` holds the Income step's ten amounts (`IncomeInfo.SOURCE_FIELDS`, `monthly_gross_wages` … `monthly_other_income`), each nullable with no default: an amount the filer never gave stays NULL, because a $0 default would pass every earlier filer's means test. The old six-month `monthly_income` is read-only and no longer written; it stays one release, and a filer who has only that total is asked on the Income step to split it. CMI is one function, `current_monthly_income` in `apps/eligibility/cmi.py`, used by the means test, the above-median calculator and the forms' `cmi` rule: the ten without Social Security (DIG-49), an empty one counting as zero once another was given, rounded to the cent half-even. With all ten empty it raises `IncomeNotSplit` ("Enter your income by source on the Income step."): a 422 from the forms views, a 400 from `calculate_means_test`. So a filer with no income at all enters $0 in one box, as the Income step's help text says, and a zero-income fixture sets one amount to 0, not all ten to null. The API's read-only `total_monthly_income` is the ten added up, Social Security included, or null. The wizard loads the ten through `hydrateAmounts` and saves `{income_info: {<the ten>}}` alone, a blank box as null, never $0 unless typed: echoing a wizard-created row's blank `marital_status` back is a 400. Schedule I lines 10 and 12, 106Sum line 4 and Schedule J 23a print the Schedule I income total (rule `schedule_i_income_total`, which 23a binds through its alias `schedule_j_total_income`; all ten sources, Social Security included); CMI, without it, prints on 122A-1 lines 11 and 12b (annualized), 106Sum line 8 and 122A-2 line 1.
- **The fee-waiver application** — `FeeWaiverApplication.monthly_take_home_pay` (encrypted, zero or more; 103B line 2) and `receives_noncash_assistance` (`BooleanField(null=True)`; 103B line 3) have no defaults and stay empty until the filer answers. Line 3 prints an empty answer blank and a stored False as a sworn "No", so never default it. `benefit_types` holds the "What kind?" answer: required with Yes, `[]` with No. A create requires both answers in every encoding, JSON or form-encoded (400 otherwise); the yes/no can't be sent empty, even in a PATCH, and kinds sent to a row with no answer are refused. `monthly_income`, `monthly_expenses` and `receives_public_benefits` are no longer written and stay one release. `GET /api/intake/fee-waiver/?session=<id>` reads one session's application and never creates one, since an application puts 103B in the packet; the page opens with it, so saved answers win over pre-fills, and take-home pay is never pre-filled. A PATCH can't move an application to another user's session (DIG-178). 103B prints take-home pay on line 2 (`undefined_2`, `undefined_4`, `undefined_6`), the answer and its kinds on line 3 (`check 3`, `3 type`, kinds only under a Yes), and Schedule J line 22c on line 6 (`undefined_7`); `4 type` and `5 Type` are unbound.
- **Expense names are the backend's** — the Expenses step and the wizard's hydration use `EXPENSE_FIELDS` (`types/api.ts`), the 13 `ExpenseInfo` names that Schedule J, 122A-2 and the means test read; the E2E page object fills `input[name=<key>]` from the personas' canonical keys. DRF drops any other name silently: the old frontend names (`car_payment`, `food_groceries`, `other_necessary_expenses`, ...) saved as $0 until DIG-45. The API returns these amounts as decimal strings; the wizard converts them with `hydrateAmounts` when it loads the session.
- **Upload areas decide the document type** — `DocumentUploadPage`'s `UPLOAD_AREAS` maps "Bills and statements" → `creditor_bill`, "Pay stubs" → `pay_stub`, "Credit report" → `credit_report`. The backend stores whatever type is sent (`user_declared_type`) and never classifies. Each `FileDropZone` is named `${label}: drop files here or click to upload` with its file input inside.
- **MSW can't parse jsdom uploads with `request.formData()`** — undici rejects jsdom's `File`, so the read fails. Read multipart fields from `await request.text()`, as `sentDocumentType` in `DocumentUploadPage.test.tsx` does.
- **Upload page locator contract** — E2E depends on each zone's name `${label}: drop files here or click to upload` (file input inside), `<ul aria-label="Upload queue">`, a read row's "✓ Done", the h1 "Upload your documents", the `role="alert"` region, and the button reading exactly "Skip for now" until a file is read, then "Continue". Don't reword them.
- **Upload rows check themselves** — each `UploadQueue` row polls its document at once, then every 3 s, waits 6 s, 12 s, 24 s… on 429/5xx/network errors, and shows "unchecked" after 2 minutes. `pollDocument` still goes through `apiFetch`'s `withRetry`, so a 5xx is retried 3× inside each check. The page reads only `status`, `failure_reason` and the area's type, never `error_message`. Files send one at a time; areas and the button are disabled only while a file is sending, not while rows are checking.
- **`uploadDocument` uses raw `fetch`** — `apiFetch` forces `Content-Type: application/json`, which breaks the multipart boundary. It handles its own 401 (one `attemptTokenRefresh()`, one retry) and throws `APIClientError` with the HTTP status; a 400 is how the server refuses a file type.
- **user-event hangs under vitest fake timers** — RTL's `asyncWrapper` drains every user-event action with a `setTimeout(0)` that only a `jest` global advances, so `userEvent.setup({ advanceTimers })` doesn't help. Under `vi.useFakeTimers()` use `fireEvent` + `act(() => vi.advanceTimersByTimeAsync(ms))`, step the clock in ≤1 s increments when each timer's reply schedules the next one, and switch back to real timers before any `userEvent` action, `findBy` or `waitFor`.

## Architecture (quick)

- **Backend:** Django 5.0 + DRF, Python 3.11, PostgreSQL 15, `encrypted-model-fields` (Fernet PII encryption)
- **Frontend:** React 19 + Vite 7 + TypeScript, Context API (not Redux), react-router-dom v7
- **PDF:** pypdf fills official AO court templates. Each schema in `data/forms/schemas/` binds a field to a widget's full name in the field index (`data/forms/field_index/<template stem>.index.json`). `build_field_values(form_type, session)` checks the form's preconditions and resolves its schema; `PDFFormFiller().fill(form_type, values)` fills exactly those full names in the template from `data/forms/pdfs/` and raises `UnknownField` for any other name.
- **PDF templates:** 67 official AO court PDFs in `data/forms/pdfs/` (committed). Baked into Heroku image.
- **Forms:** 17 form types in `apps/forms/registry.py` (`FORM_REGISTRY` / `get_all_form_types()` / `packet(session)`). `generate_all` gives each form its own savepoint.
- **OCR service:** provider-agnostic. `OCR_PROVIDER` selects `openai` (default, `gpt-4o`, `OPENAI_API_KEY`) or `gemini` (`gemini-2.0-flash`, `GEMINI_API_KEY`); `OCR_MODEL` overrides the model so a model change is a config var, not a deploy. No local model — both call a hosted API directly.
- **Auth:** JWT (simplejwt). Access in memory, refresh in localStorage. `POST /api/token/obtain/` + `/api/token/refresh/`.
- **E2E:** 6 AI persona briefs in `docs/testing/persona-briefs/` (andres, deshawn, james, maria, priya, sarah) driving 8 journey specs — one per persona plus `sofa-journey.spec.ts` and `scanned-bill-journey.spec.ts` (an upload read through a fake OpenAI server). `seed_demo_data` creates synthetic sessions with all intake data.
