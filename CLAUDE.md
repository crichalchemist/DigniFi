# AI Assistant Context

**DigniFi** — trauma-informed bankruptcy filing platform (Chapter 7, ILND pilot district). Django REST API + React 19 frontend. Deployed on Heroku. Provides legal _information_, never _advice_ (UPL boundaries are non-negotiable).

## Quick Commands

```bash
docker compose up                              # Start all 3 services (db, backend, frontend)
docker compose exec backend python -m pytest --ds=config.settings.test -m "not slow"    # Fast backend run, about 2 min (sqlite :memory:, no postgres needed)
docker compose exec backend python -m pytest --ds=config.settings.test    # Full backend run, as CI runs it (CI adds --cov, which roughly doubles the time)
docker compose exec backend python manage.py migrate
docker compose exec backend python manage.py loaddata ilnd_2025_data   # Required before seed
docker compose exec backend python manage.py seed_demo_data            # Loads 6 AI personas

cd frontend && npm test                        # Frontend tests (vitest)
cd frontend && npm run e2e                     # E2E (requires backend running + seeded)
cd frontend && npm run lint:fix && npm run format
cd backend && ruff check . --fix               # Backend lint (pinned ruff==0.8.5)
```

## Gotchas (things agents get wrong)

- **DRF pagination** — list endpoints return `{count, results}`, not bare arrays. Always `Array.isArray` guard.
- **React 19 + navigate()** — calling `navigate()` in render body crashes the reconciler. Use `useEffect`.
- **Vite HMR in Docker** — type/structure changes don't hot-reload; restart the frontend container.
- **Enum mismatches are silent** — frontend/backend enum drift only surfaces at runtime; check both when adding fields.
- **Nested debts and assets save by id** — `IntakeSessionSerializer.update` upserts `debts`/`assets` through `_save_rows_by_id`: a row carrying one of this session's ids updates only the keys it sends, a row without one (or with an unknown or foreign id) is created on this session, and a stored row missing from the payload is **deleted**, so send every row you want to keep. A nested `session` is ignored. A session PATCH or PUT that carries `assets` or `debts` returns that list in the order it was sent, each row with its id (a new row, or one sent with a foreign or unknown id, shows its new id), so the wizard can pair rows by position and keep a new row's id; every other read of assets goes by id (`AssetInfo` has no `Meta.ordering`: `AssetViewSet` orders by `pk` and the session serializer sorts the nested list), and debts keep model order (DIG-164). An asset row is a Schedule A/B row (3b): `ab_line` (a catalog key, or null on an old row, which round-trips), `details` (replaced whole on a save; a `kind` must be on that line, `percent` is stored as a string, and a figure sent with its `value_unknown`/`entire_unknown` flag clears the flag), `description`, `current_value` and `entire_value` (nullable, `min_value=0`, so $0 saves and comes back as `"0.00"`, and a value wider than `DecimalField(12, 2)` is a 400). `asset_type` is read-only, and `equity`, `account_number` and `financial_institution` are off the API. A session PATCH or PUT may also carry `asset_lines`, `{line: "yes"|"no"|null}`: it sets only the keys sent (null clears one), an unknown line or answer is a 400, and it locks the session and reopens a completed intake like any intake-data write. The Assets step saves the whole step (every row and every answer) each time. `POST /assets/` (the per-item path) refuses a row with no `ab_line`. The wizard holds the Assets and Amounts Owed rows itself (`AssetsStep`/`DebtsStep` are controlled: `rows`, `onRowsChange`) and gives each row a browser-only `_key`, a loaded row's id or `new-<n>` from a counter in the step for a new row (not `crypto.randomUUID()`, which plain HTTP from another device lacks), which `saveCurrentStepData` leaves out of the request. After a save it writes the id at each position into the row with that `_key`, wherever it now sits, skips a row removed while the save was on its way, and takes nothing else from the reply, so amounts stay as typed. Only the newest save of a list writes ids: a reply that lands after a later save of the list has gone out (an autosave, or Continue, on a slow link) changes nothing, since the later save left without this reply's ids and the server has already replaced any row the earlier save created, so a save that went out after an earlier reply never carries an id that reply replaced. One case is not covered: a session PATCH that fails and is retried by `withRetry` (`api/client.ts`) can land on the server after a newer save (Continue during the retry's 0.5–3.5 s backoff), so the server keeps the older save's values and the browser can hold an id the server deleted. A reply whose list is a different length from the one sent fails the save rather than pairing ids by guesswork. Fields the browser never receives (`account_number`, `source_document`) survive a re-save. `DebtViewSet`/`AssetViewSet` keep the base serializers, so per-item create never takes a client id. Contracts and codebtors save the same way, as a whole list: `PUT /intake/sessions/{id}/contracts/` (or `codebtors/`) checks every row before writing any, and an empty list deletes every stored row. The wizard sends each list on Continue from steps 7 and 8, and reads both with the session before any step shows, so a list that failed to load is never saved as empty. The Income step's household rows are held by the wizard the same way, as `householdRows` with a `_key`. They pair ids under `listSavesRef.members`, and only the newest save writes them. The Income step's business and rental entries are held the same way, as `entryRows`/`spouseEntryRows`, and pair under `listSavesRef.entries`/`spouseEntries`. One session reply pairs every list it carries: members, entries and the spouse's entries. The server's rules for those rows differ: see "The household list".
- **Saves lock the session** — every write to a session's intake data first calls `lock_session` (`apps/intake/locking.py`, `select_for_update` on the session row) inside the same `transaction.atomic()` block as the write, so a second save of the same session waits for the first to commit and then reads what it stored (DIG-188). That covers the session PATCH and PUT, `update_step`, `complete` (which writes only `status` and `completed_at`), the contracts and codebtors PUT, POST and DELETE, the filing-fee PUT (`PUT /intake/sessions/{id}/filing-fee/`, which never reopens), the `DebtViewSet`/`AssetViewSet` writes, a scanned bill's correction and an upload's findings. Call `get_object()` before locking (another user's session is a 404), and lock before reading anything the write depends on. An upload locks only in its worker thread, around the write of its findings, after the call to the hosted model: the upload request waits for that thread, so a lock taken in the request deadlocks. `select_for_update` does nothing on sqlite, so the backend suite can't see a missing lock; only `apps/intake/tests/test_session_lock.py` (marker `postgres`) proves it, and it skips under the default settings. Run it locally with `DJANGO_SETTINGS_MODULE=config.settings.test_postgres pytest -m postgres`, with `DATABASE_URL` naming a Postgres whose user can create the test database; CI runs it in the backend job against its Postgres service. `test_postgres` sets a 10-second `lock_timeout`, so a deadlock fails a test instead of hanging the run. The session PATCH's lock covers its `household`, `spouse_income`, `income_info` and `asset_lines` keys, and the lock test's `WRITES` holds the household and income PATCHes and the filing-fee PUT.
- **Debt and asset amounts are readable, as strings** — the owner gets `DebtInfo.amount_owed` and `AssetInfo.current_value`/`amount_owed` back (SSN and `account_number` stay write-only). DRF sends decimals as strings (`"2500.00"`), so the wizard converts them with `hydrateAmounts` (`utils/parseAmount.ts`) as session data enters step state; a raw string in a step's `reduce` joins as text (`$02500.00100.50`). A stored amount wider than `DecimalField(12, 2)` makes every read of that session 500, so every write path must bound it (`DraftDebtCreator` stores it as 0; documents `validate` returns 400).
- **Seed order** — `seed_demo_data` requires `loaddata ilnd_2025_data` first (the seed writes `current_step=7`, Contracts & Leases), or means test has no median income data. It reads the median table in force on today's real date, not the tests' pinned one, and when none is (from April 1, 2027 until the next table is loaded) it prints a message naming `docs/REFERENCE_TABLES.md` and changes nothing, so even `--reset` leaves the existing personas. Personas seeded before income was stored by source must be re-created with `seed_demo_data --reset` (migration 0014 leaves their totals unsplit, and a plain re-run skips existing users). The seed writes each persona's `Household` and `SpouseIncome` before it runs the means test. Personas seeded before 3e1 have no line 1 answer, household list or county, so the means test refuses them in the Income step's words, and so does every forms call that gets past the Assets step's check (a persona seeded before 3b has no A/B answers, so Generate, Generate All, Regenerate and an unfiled download answer with the Assets sentence first, `AssetStepGap`). Re-create them with `seed_demo_data --reset`. Personas seeded before 3e2 have no business and rental list or 'now different' answer, so the means test refuses them in the Income step's words, and every forms call does once the Assets step's check passes. Re-create them with `seed_demo_data --reset`. The seed writes each person's 3e2 answers (the list `[]`, except Andrés's one business entry (Rideshare and delivery driving), "now different" No, assistance, deductions, Schedule J line 3) and stamps `income_period_end` with today's window. The seed also writes each persona's `FilingFee`. Maria and Sarah ask for the waiver, with 103B lines 4, 7 and 9 No and their own line 5; DeShawn and Andrés pay in installments; James and Priya pay in full. Personas seeded before 3f have no `FilingFee`, so once the Assets step's check passes their Form 101 is refused with a link to `/filing-fee`. Maria, DeShawn and Sarah are the exception: migration 0030 gives each of them `waiver`, with 103B lines 4, 5, 7 and 9 unanswered, so their 103B is refused instead, again only once the Assets step's check passes. Re-create them with `seed_demo_data --reset`. Personas seeded before 3b have old asset rows and no line answers, so Complete and the four forms calls that run `_prepare` (Generate, Generate All, Regenerate and an unfiled download) refuse them with the Assets sentence first; the packet list never runs that check. Re-create them with `seed_demo_data --reset`.
- **Each form counts the household list its own way** — each count lives in `apps/intake/household.py`, a pure module with no models. `count_family_size` is the filer plus every row that lives with them; it feeds 122A-1 line 13 (`13B`, the `family_size` rule), the means test's median and `household.family_size`, and this reading is a draft until counsel rules on C-3. `count_exemptions` is the filer plus every row answered Yes to "claimed or supported"; it sizes the expense calculator (122A-2 line 5's definition), whose fallback to 1 on an error stays until DIG-152; the line itself stays unbound until 3h. `dependents` is Schedule J line 2: every non-spouse row claimed or supported, and the spouse's row only when "Is your spouse a dependent of yours?" is Yes. `count_fee_waiver_household` is 103B line 1: the filer; the spouse once, for `married_spouse_filing` or `married_together`; and the dependents, leaving out a spouse already counted. `DebtorInfo.household_size` and `filing_type` stay in their table, unread and off the serializer, until step 5 drops them. `IncomeInfo.number_of_dependents` is gone (migration 0019). Schedule J line 1 (`schedule_j_joint_case`) prints "no" for every session.
- **The household list** — `Household` is one-to-one with the session. Its `county` is encrypted and must be one of `ILND_COUNTIES`, or it is a 400. Its `members` are encrypted JSON: null means unanswered, and `[]` means the filer said no one. Step 1 sends `{household: {county}}` and step 2 sends `{household: {members}}`; the serializer updates only the keys sent. Ids come from `next_member_id` and are never reused: a row sent with one of the list's ids replaces the stored row whole, a row with no id, an unknown id or a repeated one gets a new id, and the reply lists the rows in the order sent, each with its id. One row shape: `id, relationship, age, lives_with_you, claimed_or_supported`, then `spouse_is_dependent` on the spouse's row only, with null for an unanswered question; `HouseholdSerializer.to_representation` returns the stored rows as they are. No names are stored. A 400 is only for a value no answer can have: an unknown relationship, an age outside 0–120 or not whole, a second spouse row, `spouse_is_dependent` on another row, or a 21st row. A missing answer saves, and Complete names it. `household.family_size` and `household.fee_waiver_household_size` are read-only, and null while `income_step_gaps` finds a gap. Two backend tests pin the frontend's copies of the server's words: `test_household_frontend_copy.py` pins `RELATIONSHIP_WORDS` to `frontend/src/constants/household.ts` and `ILND_COUNTIES` to `counties.ts`. The forms' own words (line 1, its declaration, the glossary sentence) live in `formText.ts`, which no reading-level test scores. DigniFi's own sentences go in `copy.ts`.
- **The packet decides which forms a filer gets** — `apps/forms/registry.py` maps each form to `applies(session)` and `requires(session)`. 103B applies only when the filer's Form 101 line 8 answer, `FilingFee.payment_choice`, is `waiver` (`_asks_fee_waiver`); 122A-2 only when `MeansTest.calculated_cmi × 12 > median_income_threshold`, through `is_above_median` (`apps/eligibility/cmi.py`), the means test's own comparison, so income exactly at the median counts as below (DIG-136). Never read `above_median_calculated`: a row calculated before DIG-128 was fixed can still carry a stale True. 122A-1Supp not until step 4; 122B is gone. A packet holds 14–16 forms. Generate All, Generate, Regenerate, the download of an unfiled form and the packet list of a completed intake work the means test out again from the stored intake first (`_recalculate_means_test` in `apps/forms/views.py`), so a stale `MeansTest` row never decides the packet (DIG-160); an unfinished intake's packet list reads the stored row. `generate` on a form outside the packet, or with a missing precondition (`PreconditionMissing`), is a 422 in plain words, and so are an Assets step gap (`AssetStepGap`, the first of `asset_step_gaps`, which comes before the means test) and an Income step gap (`IncomeStepGap`, the first of `income_step_gaps`; income not entered by source is one), no median table in force on the fill date (`NoTableInForce`, which logs the table, the date and the district), and a letter the form's font can't print (`UnprintableLetter`) or a value too long for its box even at 6 pt (`ValueTooLong`), whose sentences name the box; so are an unfinished intake, a form marked filed and a value that matches none of a box's choices (`UnmappedChoice`), each in a fixed sentence (see the gotchas below), and any other failure while the form is prepared, resolved or checked is a 500 logged by exception type only. A request without a session id or a known form type is a 400 before any of this, and a session id that names none of the filer's own sessions a 404. Form 101's `requires` is `_needs_debtor_info_county_and_fee_choice`, so a missing county, and then a missing line 8 answer ("Choose how you will pay the filing fee."), is its `PreconditionMissing`. 103B's is `_needs_fee_waiver_answers`: lines 4, 7 and 9 answered, each Yes with its text, and line 5 not blank once trimmed, the first gap in the form's order refused. Both refuse with `page="/filing-fee"`. A `PreconditionMissing` carries a `step` or a `page`, never both, and a raise names it as a literal, which `test_rule_fixes.py` reads from the source.
- **Forms need a completed intake** — through the API, only the session's `complete` action sets `status="completed"`: `status` and `current_step` are read-only on `IntakeSessionSerializer`, and `update_step` takes only a whole number from 1 to 9 (anything else is a 400). Complete refuses with a 400 `{message, errors: [{step, message}]}`, one entry per gap in wizard order, each `step` a `WIZARD_STEPS` key: no `DebtorInfo` row (the name-and-address sentence; the fields themselves aren't checked) or an SSN that isn't 9 digits (the registry's own `_needs_ssn`, so Complete and Forms 101 and 121 say the same thing), a missing county (`_needs_county`, step `debtor_info`), then every gap of `income_step_gaps` in this order (marriage unanswered; "spouse is filing with you"; the household list unanswered, null and not `[]`; a row with an unanswered question; the list and the marriage answer disagreeing, judged only on answered data; a legacy rental figure; income not entered by source, not named while the legacy gap is; then the business and rental list unanswered, null and not `[]`; an entry with an unanswered question (kind, a description not blank once trimmed, gross, expenses, and both current amounts while "now different" is Yes); "now different" unanswered; "now different" Yes with no current figure; assistance unanswered; assistance Yes with no kind, or an amount beside an empty kind; a cash kind with no cash amount; and, under `married_together`, the spouse's legacy rental figure, the spouse's income not entered and the same seven for the spouse. A person with no income row counts as every answer unanswered.) Then a person whose Schedule I line 4 is above $0 with all eight deductions blank (step `take_home_pay`, the filer then the spouse at home), an Expenses step never saved (no `ExpenseInfo` row), Schedule J line 3 unanswered (step `expense_info`), then every gap of `asset_step_gaps` (`apps/intake/asset_lines.py`, step `assets`, in the form's order: an old row with no line, named by its description; a shown line with no Yes or No; Yes with no row; No, or a line a gate's No hides, with rows; a gate that says Yes with every line under it No; a row on a gate line, which takes no items; and a row missing what its shape needs, naming the row), and a scanned debt the filer hasn't confirmed (a `DebtInfo` with `is_draft`, step `debts`; see "Document upload sits mid-wizard"). The forms views refuse any other status with a 422, "Finish your intake before preparing your forms.": Generate All once for the whole call, before it deletes anything; Generate, Regenerate and the download of an unfiled form through `_prepare`. `_prepare` then raises the first `AssetStepGap` (a 422 `{error, step: "assets"}`, like `IncomeStepGap`) before it works the means test out, so a session completed before 3b can't print A/B totals from rows no line owns; the packet list and a filed form's stored download never run it. The packet list never refuses an unfinished intake. A forms refusal also carries the `step` (a wizard step key) or `page` (a route) that fixes it, when the exception names one: `PreconditionMissing.step` or `.page` (`/filing-fee` for Form 101's line 8 and 103B's own questions), `IncomeNotSplit.step` (`income_info`), `IntakeNotFinished.page` (`/intake`) and the `step` or `page` of an `UnprintableLetter` or `ValueTooLong`, from the binding that feeds the box (`fix_for` in `fill_resolver.py`); "already filed", "not in your packet", `NoTableInForce` and the download of a filed form whose stored values hold a letter or a length `check()` refuses carry neither, and the key is absent, never null. The check lives in the views, not in `build_parts` or `build_field_values`, so forms view tests need a completed session, with income by source and a district with a median table in force on the fill date, since Generate All, Generate, Regenerate, an unfiled download and a completed intake's packet list work the means test out. Every intake-data write sets a completed session back to `in_progress` through `IntakeSession.reopen()`, so the filer presses Complete again: a session PATCH carrying `debtor_info`, `income_info`, `expense_info`, `debts`, `assets` or `asset_lines`; the contracts and codebtors endpoints; `DebtViewSet`/`AssetViewSet` writes; an upload that adds a draft debt or pay-stub figures, and a correction to a scanned bill or pay stub. `update_step` (Continue) sets `in_progress` itself. Form answers (`answers/bulk`), SOFA and the filing fee (`PUT /api/intake/sessions/{id}/filing-fee/`) never reopen it; a new intake-data write path must lock the session first (see "Saves lock the session") and call `reopen()`. A failed Complete or means-test call keeps the filer on Review (DIG-150), and the dashboard shows a "Finish your intake" link back to the wizard until the session is complete. A forms refusal's `step` also comes from `AssetStepGap.step` (`assets`) and `IncomeStepGap.step` (`income_info`). Forms view tests need the 3e1 answers too: `answer_household` (`apps/intake/tests/builders.py`), whose defaults are `not_married`, a list of `[]`, county `Cook` and a `FilingFee` paying in full, so Form 101 has its line 8 answer (`payment_choice=None` leaves the record as it is). `answer_household`'s 3e2 defaults are "now different" No, the list `[]`, assistance No and `payroll_tax` $0, and a test that presses Complete also sets `expenses_include_others`. The writes that reopen a completed intake gain `household`, `spouse_income` and `asset_lines` in a session PATCH. `answer_household`'s `asset_lines` default is none (every shown Schedule A/B line answered No, through `answer_asset_lines`), so a session with no property passes Complete; a test with a row names its lines Yes, and `asset_lines=None` leaves the stored answers alone.
- **SSN on forms** — Form 101's `Debtor1.SSNum` gets the last 4 digits from the `ssn_last_4` derivation; the full SSN appears only on Form 121.
- **Means test units** — CMI is monthly, Census median is annual. `MeansTest.calculate()` annualizes CMI ×12 per § 707(b)(7). The original bug passed everyone. `MeansTest.calculate()` annualizes the household's CMI, `household_cmi`: the filer's, plus the spouse's for `married_together` only, each column rounded to the cent. `calculation_details` holds `marital_status` (the line 1 answer), `family_size` (line 13) and `spouse_cmi` (Column B), and no `number_of_dependents`. The means test gives no fee-waiver verdict (3f dropped its flag, eligibility migration 0003): the court decides the waiver, and the filing-fee page shows its figures as information. `calculation_details` also holds `business_net`, `rental_net`, `spouse_business_net` and `spouse_rental_net`, the floored nets CMI added.
- **Dated tables and the fill date** — `in_force(rows, on, table, district)` (`apps/districts/dated_tables.py`) takes the newest row whose `effective_date` is on or before `on` (later rows are ignored) and returns it unless its `valid_through` is set and earlier than `on`; when that row has expired, or no row has started yet, it logs one line (the table, the date and the district) and raises `NoTableInForce`, a `ValueError` carrying the filer's sentence, and never looks at an older row. Every lookup of a dated table takes `fill_date()`, the day the forms are filled in America/Chicago, which stands in for the filing date. The root `backend/conftest.py` pins `_today` to 2026-10-16 for every backend test, so a test of a lookup sets its own day with `monkeypatch.setattr("apps.districts.dated_tables._today", ...)`, and no module may import `_today` by name. A scheduled row (`DatedTable`: `effective_date`, `valid_through`, `source_url`) carries `valid_through`, the day before its next scheduled change, and an empty one means open-ended; a test fails on a fixture median row without one. `PovertyGuideline` (`apps/districts/models.py`) holds the HHS poverty guidelines for the 48 states and DC. It is national, so it has no district, and its rows come from data migrations, not a fixture: `0005_poverty_guideline_2026` loads 2026 ($15,960, and $5,680 for each additional person), effective 2026-01-15, the Federal Register publication date, through 2027-01-31. So every database, CI and the Heroku release have the rows without `loaddata`, and a new year is a new data migration. `poverty_guideline_in_force(on=None)` (`apps/districts/poverty.py`) looks the guideline up through `in_force` on `fill_date()` as `POVERTY_TABLE` ("HHS poverty guidelines"), and logs `for district -`. `poverty_limit_monthly(guideline, family_size)` is the court's 150% limit a month, rounded half-up to the cent ($1,995.00 for one person and $710.00 for each person after, in 2026). It decides nothing: comparing a family's income with it is the court's job. Nothing that prepares a form reads the guideline. A transactional test's teardown empties every table, the migrated rows included, and pytest-django runs those tests after the `db` tests: a plain `db` test may rely on the migrated 2026 row, and any other test that needs it asks for the root `backend/conftest.py` fixture `poverty_2026`, which puts it back. The 2026 row ends two months before the median table does: from 2027-02-01 the filing-fee page shows its no-table sentence and the journeys' limit checks fail until the 2027 row is loaded. The dev server, the seed and E2E use the real date, so from April 1, 2027 (the November 2026 update was not posted, so the April 2026 row runs to March 31, 2027) the forms calls that work the means test out (Generate All, Generate, Regenerate, a completed intake's packet list, and the download of an unfiled form or of a filed one with no stored values), the means test, `seed_demo_data` and CI's E2E job refuse until the next median table is loaded. `docs/REFERENCE_TABLES.md` says where each table is posted and how to add a row.
- **GenerateAll vs single** — `/generate_all` returns `{generated, errors}`; single returns `{form, message}`. Generate, Generate All and Regenerate check without drawing: each resolves the form's parts (`build_parts`), runs `PDFFormFiller.check()` and stores them, so a letter the form can't print or a value too long for its box is a 422, or a Generate All `errors` entry, carrying its `step` or `page`. `check()` composes the text first (NFC, in `pdf_filler._as_printed`, which the sheets use too), so a letter typed as a letter and a combining mark, such as e and U+0301, is checked and printed as the one letter é. The browser sends Generate All once (`apiFetchOnce`, never `withRetry`), and the dashboard links each refusal it shows (the packet list's, Generate All's whole-call refusal, a Generate All `errors` entry, or a card's refused Generate or Download, whose body `downloadForm` reads after its one token refresh) to its fix: a `step` to `/intake?step=<key>`, a `page` to that page when the dashboard has words for it (`PAGE_LINK_LABELS` in `FormDashboard.tsx`: `/intake`, `/filing-fee`, `/sofa` and `/documents`; or, for `/ask/<form type>`, that form type's label in `FORM_TYPE_METADATA`), so a new fix page needs its words there, "Finish your intake" at most once. A card's refusal stays until its own Generate or Download next succeeds, Generate All answers with its `generated` and `errors` (which then hold every checked form's current refusal, so none shows twice as it answers, though a card's own refusal after that can repeat one; a filed form, which Generate All returns unchecked, shows none until its next Download; a refusal of the whole call leaves the cards' as they are), or the form is marked filed. Download draws: `fill()` bakes with PyMuPDF, which isn't thread-safe, so the server stays on sync gunicorn workers with no `--threads` unless the bake gets a lock. Generate calls PyMuPDF too, without drawing: `check()` measures an attached sheet's text with PyMuPDF's `Font` (`sheets.plan_sheet`), and so does the startup check. A refusal of the whole call is `{error}` with no `form_type` (plus its `step` or `page`, as in "Forms need a completed intake"): Generate All for an unfinished intake (422), and Generate All for an Assets step gap (`AssetStepGap`, `step: "assets"`; the packet list never checks it), and Generate All or a completed intake's packet list for an Income step gap (`IncomeStepGap`, income not entered by source among them) or no median table in force on the fill date (both 422). `generate_all` covers only the packet and deletes the rows of unfiled forms that no longer apply. A form marked filed keeps its stored answers, even after it leaves the packet (DIG-155): `generate_all` leaves it untouched and returns it in `generated`, in its packet position, or after the packet's forms once it has left the packet; its download draws its stored `field_values` without the packet check, and a letter or a length in them that `check()` refuses is a 422 with no `step` or `page`, as is a template with no form (`TemplateHasNoForm`, in its own sentence, which only a download meets, since only a download draws), while any other refusal of them, such as a key, box state or option the template no longer has, is a 500; `generate` and `regenerate` return 422 for it, but only after the completion check, the Assets step's check and the means test, whose refusals come first. The current ten are left out of the body under No or unanswered (the server keeps what an earlier Yes stored, and the wizard keeps the typed figures), and the five assistance fields (`assistance_answer`, `cash_assistance_kind`, `cash_assistance_amount`, `noncash_assistance_kind`, `noncash_assistance_value`) are always sent, a blank amount as null and a blank kind as `""`; the spouse's follow their own `income_now_different`. Step 3's body, Take-home pay, is `{income_info: {the eight deductions, payroll_other_specify}, spouse_income: {the same}}`, with `spouse_income` only while the answer is `married_together`. A blank deduction is sent as null. Neither step's body carries the other's keys, so neither saved copy overwrites the other. Lines 4, 6 and 7 are shown and never sent. Step 4's body, Expenses, is `{expense_info: {the 26 amounts, a blank as 0; taxes_specify, support_others_specify and other_expenses_specify, a blank as ""; expenses_include_others, unanswered as null}}`. `household.family_size` and `household.fee_waiver_household_size` stay out of the body. A save of the household list returns its copy with ids, as assets and debts do.
- **An empty scan is FAILED, not done** — `documents/views._record_findings` judges each type: a bill needs a creditor name, a pay stub must pass `PayStubExtraction`, the check the income aggregate applies (gross pay + both pay-period dates required; an invalid optional field such as a negative `net_pay` also fails it), a credit report needs one readable tradeline. Otherwise `OCRResult.status="failed"`, `failure_reason="nothing_found"`; any exception is `processing_error`. A bill with a creditor but no readable balance is `completed` with a $0 draft; a report of only $0 accounts is `completed` with no debts. Other document types are not judged.
- **The documents API never returns `error_message` or `extracted_data`** — `_serialize_ocr` returns `status`, `failure_reason`, `confidence_scores`, `overall_confidence`, `user_validated`. `error_message` is operations-only (exception class, `finish_reason`); read it in a Django shell. The pipeline's catch-all handlers (`_run_processing`, `AggregateIngestionService.recalculate`) log only the exception's type with `logger.error`, never `logger.exception`: logs reach Sentry, and a DB error's DETAIL quotes row values (DIG-105).
- **Scanned amounts are bounded** — `draft_debt._bounded_amount` stores a non-numeric, negative, non-finite or ≥1e10 balance as 0, and `TradelineItem.amount_owed` has `le=9999999999.99`: a wider value makes `DecimalField(12,2)` raise on every read of the session.
- **Prompt hints are per type and shared** — `_FIELD_HINTS` in `documents/services/providers/prompts/image_extraction.py` feeds both the vision and the text prompt (`text_extraction.py` imports it). A type with no hint is asked for "all visible fields as key-value pairs" and never returns the keys its importer reads; the `CREDIT_REPORT` hint's keys must stay in step with `TradelineItem`, and `test_prompts.py` checks that they do.
- **Income is stored by source** — `IncomeInfo` holds the Income step's ten amounts (`IncomeInfo.SOURCE_FIELDS`, `monthly_gross_wages` … `monthly_other_income`, interest and dividends (`monthly_interest_and_dividends`) among them, rental no longer), each an `EncryptedDecimalField`, nullable with no default, declared on `IncomeInfoSerializer` as `DecimalField(10, 2, min_value=0)` (DRF would map the encrypted field to a 20-character string): an amount the filer never gave stays NULL, because a $0 default would pass every earlier filer's means test. `monthly_rental_income` is the legacy net rental figure: encrypted, read-only on both serializers (a write is ignored), and read only by the legacy gap (`LEGACY_RENTAL`, `SPOUSE_LEGACY_RENTAL` in `income_step_gaps`), which names it while it is above $0 and that person's `business_and_rental` list is unanswered, and keeps 'income not entered' unnamed for that person meanwhile. A save carrying the list clears it. `IncomeInfo` and `SpouseIncome` share the abstract `IncomeDetail`: the list (encrypted JSON, null unanswered, `[]` none, server ids from `next_entry_id`, at most 10, `store_entries`/`get_entries`), the ten `CURRENT_FIELDS`, `income_now_different`, the assistance answers and the eight `DEDUCTION_FIELDS`, all encrypted; `_save_income`/`_save_spouse_income` set only the keys sent. The old six-month `monthly_income` is encrypted JSON text, read-only (`get_monthly_income()`; the API returns the array) and no longer written; it stays one release, and a filer who has only that total is asked on the Income step to split it. `current_monthly_income` in `apps/eligibility/cmi.py` works on one person's ten amounts and their business and rental list: the ten without Social Security (DIG-49), plus that person's floored business net and floored rental net (`apps/intake/income.py`: each kind's gross sum less its expenses sum, from the averages, never below $0.00, C-12; a loss never crosses kinds or people), an empty one counting as zero once another was given, rounded to the cent half-even. With all ten empty and no entry figure it raises `IncomeNotSplit` ("Enter your income by source on the Income step."): a 422 from the forms views, a 400 from `calculate_means_test`. So a filer with no income at all enters $0 in one box, as the Income step's help text says, and a zero-income fixture sets one amount to 0, not all ten to null. The API's read-only `total_monthly_income` is the ten added up, Social Security included, plus the floored nets, or null. Continue from the Income step (`update_step` 3) stamps `IncomeInfo.income_period_end` with the window's last day; the session read's `income_window` is the window today. The wizard loads the ten through `hydrateAmounts` and saves the body described under "Autosave sends only real edits", a blank box as null, never $0 unless typed, the spouse's boxes too. `household_cmi` adds `spouse_monthly_income` when `counted_spouse_income` finds `married_together`; the means test, the above-median check, the expense calculator, the `cmi` rule and `line12b_annualized_cmi` read it. `spouse_monthly_income` is None unless the answer is `married_together`, and then the spouse's CMI, or an `IncomeStepGap` in the spouse's words when none of the spouse's ten amounts and no entry figure was given; `counted_spouse_income` returns the row or None and never raises. `SpouseIncome` holds the spouse's ten, encrypted and nullable, with the filer's bounds. `marital_status` is encrypted and takes one of `MARITAL_ANSWERS` or null; anything else is a 400, `single`, `married_joint` and `""` included. Schedule I lines 2–4, 8a–8e, 8g and 8h read the figures Schedule I uses: the current ones while that person's "now different" is Yes (`schedule_i_field`), the averages otherwise. 8a is the person's floored business net plus floored rental net on those figures, and 8h's words (`schedule_i_other_income_label`) follow the 8h figure; `other_income_label` stays on 122A-1 line 10. 8f (the cash amount plus the known non-cash value) prints on Schedule I only and never enters CMI (C-11). Line 7 is line 4 less line 6, and lines 10 and 12 are line 7 + line 9. `schedule_i_rental_*` is gone. Schedule I lines 10 and 12, 106Sum line 4 and Schedule J 23a print the Schedule I income total (rule `schedule_i_income_total`, which 23a binds through its alias `schedule_j_total_income`; Social Security included); CMI, without it, prints on 122A-1 lines 11 and 12b (annualized), 106Sum line 8 and 122A-2 line 1. Schedule I `Amount 10 Debtor 1` prints `schedule_i_income_total_debtor1`, and `Amount 10` and `Amount 12` print both columns. 122A-1 `Debto1.Quest11` prints `filer_cmi` and `Debto2.Quest11` prints `spouse_cmi`.
- **The filing fee** — `FilingFee` (`apps/intake/models.py`, one-to-one with the session, `related_name="filing_fee"`, table `filing_fees`) holds Form 101 line 8 and 103B's own questions, every column encrypted, and nothing starts answered: `payment_choice` (`pay_in_full`, `installments` or `waiver`; null unanswered), 103B lines 4, 7 and 9 as `income_change_answer`, `others_covered_answer` and `expense_change_answer` (`yes`, `no` or null) with their texts `income_change_explanation`, `others_covered_who` and `expense_change_explanation`, and line 5's `installments_explanation`; each text is bounded by `FilingFee.TEXT_LIMITS`, which the serializer and the page enforce. `GET` and `PUT /api/intake/sessions/{id}/filing-fee/` read and save it for a session in any status: the PUT locks the session, sets only the keys sent, refuses an unknown key or value with a 400 (`FilingFeeSerializer`), never reopens a completed intake and returns the GET body, which adds `information` (`{family_size, limit_monthly, guideline: {year, effective_date, source_url}, family_income_monthly}`, decimals as strings, from `filing_fee_information` in `apps/intake/filing_fee.py`), or null with `information_gap` `"income"` or `"no_table"`; a missing figure never blocks the answer. `FilingFeePage` (`/filing-fee`) asks every filer after Complete and shows the court's limit beside the filer's own figure as information, never a verdict ("The court decides."); `/fee-waiver` redirects there. 103B is in the packet exactly when `payment_choice` is `waiver`; its `requires` refuses an unanswered line 4, 7 or 9, a Yes without its text, or a blank line 5, with `page: "/filing-fee"`, and Form 101 refuses an unanswered line 8 the same way ("Choose how you will pay the filing fee.") and prints the answer on `Check Box7`. 103B lines 1–3 read the wizard through `apps/forms/services/fee_waiver.py`, and their refusals link to `income_info`: line 1 is `fee_waiver_family` (the filer, a spouse at home and the dependents, `count_fee_waiver_household`; an Income step gap raises `IncomeStepGap`, never a guessed 1), line 2 is `fee_waiver_income` (Schedule I line 10 per person less the counted non-cash value, the figure the page shows), and line 3 is 8f (`fee_waiver_noncash`). Line 6 prints Schedule J line 22c (`undefined_7`). A migrated `waiver` session has no answers to lines 4, 5, 7 and 9, so its 103B is refused until the filer answers them, and a session with no `FilingFee` has its Form 101 refused until the filer chooses; re-create the personas with `seed_demo_data --reset`.
- **Expense names are the backend's** — the Expenses step and the wizard's hydration use `EXPENSE_FIELDS` (`types/api.ts`), the 26 `ExpenseInfo.AMOUNT_FIELDS` names in Schedule J's order, plus `EXPENSE_SPECIFY_FIELDS` (the three Specify texts) and line 3's `expenses_include_others`; the E2E page object fills `input[name=<key>]` from the personas' canonical keys and checks line 3's radio. The backend's names are `ExpenseInfo.AMOUNT_FIELDS`, Schedule J's 26 amounts in its order (13 since step 2, 13 more since 3e2), plus three 'Specify' texts (`SPECIFY_FIELDS`, up to 100 characters) and line 3's `expenses_include_others` (`yes`, `no` or null; anything else a 400). DRF drops any other name silently: the old frontend names (`car_payment`, `food_groceries`, `other_necessary_expenses`, ...) saved as $0 until DIG-45. All are encrypted: the 26 amounts are `EncryptedDecimalField`s (default 0), declared on `ExpenseInfoSerializer` with `min_value=0`, and the texts and line 3 are `EncryptedCharField`s; `data_source` stays plaintext. The API returns the amounts as decimal strings and `total_monthly_expenses` as a number; the wizard converts the amounts with `hydrateAmounts` when it loads the session.
- **Upload areas decide the document type** — `DocumentUploadPage`'s `UPLOAD_AREAS` maps "Bills and statements" → `creditor_bill`, "Pay stubs" → `pay_stub`, "Credit report" → `credit_report`. The backend stores whatever type is sent (`user_declared_type`) and never classifies. Each `FileDropZone` is named `${label}: drop files here or click to upload` with its file input inside.
- **MSW can't parse jsdom uploads with `request.formData()`** — undici rejects jsdom's `File`, so the read fails. Read multipart fields from `await request.text()`, as `sentDocumentType` in `DocumentUploadPage.test.tsx` does.
- **Upload page locator contract** — E2E depends on each zone's name `${label}: drop files here or click to upload` (file input inside), `<ul aria-label="Upload queue">`, a read row's "✓ Done", the h1 "Upload your documents", the `role="alert"` region, and the button reading exactly "Skip for now" until a file is read, then "Continue". Don't reword them.
- **Upload rows check themselves** — each `UploadQueue` row polls its document at once, then every 3 s, waits 6 s, 12 s, 24 s… on 429/5xx/network errors, and shows "unchecked" after 2 minutes. `pollDocument` still goes through `apiFetch`'s `withRetry`, so a 5xx is retried 3× inside each check. The page reads only `status`, `failure_reason` and the area's type, never `error_message`. Files send one at a time; areas and the button are disabled only while a file is sending, not while rows are checking.
- **`uploadDocument` uses raw `fetch`** — `apiFetch` forces `Content-Type: application/json`, which breaks the multipart boundary. It handles its own 401 (one `attemptTokenRefresh()`, one retry) and throws `APIClientError` with the HTTP status; a 400 is how the server refuses a file type.
- **user-event hangs under vitest fake timers** — RTL's `asyncWrapper` drains every user-event action with a `setTimeout(0)` that only a `jest` global advances, so `userEvent.setup({ advanceTimers })` doesn't help. Under `vi.useFakeTimers()` use `fireEvent` + `act(() => vi.advanceTimersByTimeAsync(ms))`, step the clock in ≤1 s increments when each timer's reply schedules the next one, and switch back to real timers before any `userEvent` action, `findBy` or `waitFor`.

## Architecture (quick)

- **Backend:** Django 5.0 + DRF, Python 3.11, PostgreSQL 15, `encrypted-model-fields` (Fernet PII encryption)
- **Frontend:** React 19 + Vite 7 + TypeScript, Context API (not Redux), react-router-dom v7
- **PDF:** pypdf and PyMuPDF draw on the official AO court templates. Each schema in `data/forms/schemas/` binds a field to a widget's full name in the field index (`data/forms/field_index/<template stem>.index.json`). `build_parts(form_type, session)`, which the views call, checks the form's preconditions and resolves its schema into the parts document `field_values` stores (`build_field_values` returns the form's `{key: value}` instead); `PDFFormFiller().check(form_type, values)` plans the widgets each key names (a full name, or `<full name>@<page>:<tag>` for one widget) in the template from `data/forms/pdfs/`, and raises `UnknownField` for any other name; `fill()` runs it, then pypdf builds each planned widget's own appearance and PyMuPDF bakes every remaining widget into the page (every push button, Print, Reset, Save As and Add Attachment, and the second widget of each stacked pair are removed first), so the PDF it returns can't be filled in a viewer.
- **PDF templates:** 67 official AO court PDFs in `data/forms/pdfs/` (committed). Baked into Heroku image.
- **Forms:** 17 form types in `apps/forms/registry.py` (`FORM_REGISTRY` / `get_all_form_types()` / `packet(session)`). `generate_all` gives each form its own savepoint.
- **OCR service:** provider-agnostic. `OCR_PROVIDER` selects `openai` (default, `gpt-4o`, `OPENAI_API_KEY`) or `gemini` (`gemini-2.0-flash`, `GEMINI_API_KEY`); `OCR_MODEL` overrides the model so a model change is a config var, not a deploy. No local model — both call a hosted API directly.
- **Auth:** JWT (simplejwt). Access in memory, refresh in localStorage. `POST /api/token/obtain/` + `/api/token/refresh/`.
- **E2E:** 6 AI persona briefs in `docs/testing/persona-briefs/` (andres, deshawn, james, maria, priya, sarah) driving 8 journey specs — one per persona plus `sofa-journey.spec.ts` and `scanned-bill-journey.spec.ts` (an upload read through a fake OpenAI server). `seed_demo_data` creates synthetic sessions with all intake data.
