# Forms step 3c4, payments move: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each monthly payment on property gets one source, the debt or lease that pays it, so Schedule J prints it on the line the form asks for (4, 5, 17a–17d, 20a) and every total stays as it was. The two Expenses boxes that duplicated those payments retire (DIG-282). Complete and the forms refuse while a figure saved in a retired box is not covered by linked payments, or while a typed line 4 sits beside a linked first mortgage the filer hasn't confirmed.

**Architecture:**

- **One mapping.** `linked_payments(session)` in `apps/intake/claims.py` reads the session's confirmed secured debts and its vehicle leases. It returns what each Schedule J line prints, following §8.1's table. Every reader goes through it: the J rules, the new total, the means-test calculator and the two new gaps.
- **One total.** `total_monthly_expenses(session)` adds the typed sum and every linked payment. The typed sum is `ExpenseInfo.calculate_total_monthly_expenses`, now 24 amounts. The six printed total boxes read the new total.
- **Retired boxes.** `vehicle_payment` and `other_property_mortgages` leave the Expenses step, the API's readable fields and the typed sum. Their columns stay, read only by the legacy gap. `AssetInfo.amount_owed` leaves the API too. All three columns drop a release after this is live.
- **Two gaps, last.** The legacy gap (step `debts`) and the line 4 question (step `expense_info`) come after Codebtors in `claim_step_gaps`. Each step shows its question in an element of its own, which never holds Continue.
- **The wizard.** A browser copy of the sums, `linkedPayments.ts`, is pinned to the server by one case table. It feeds three things:
  - Review's three expense lines;
  - the Expenses step's line 4 question;
  - the Amounts Owed step's legacy sentence and its Remove button.

**Tech Stack:** Django 5.0, DRF, `encrypted-model-fields`, pytest-django with sqlite (and Postgres for the lock test). React 19, TypeScript, vitest with MSW, Playwright for the journeys. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-06-forms-step3c-design.md` §8 (cited `§8.x`) and §12, with the builder's calls B19–B24, B39, B45, B46 and B48 (§15). Where this plan and the spec disagree, the spec wins, except at "Rulings". `PS:<line>` cites the persona companion, `docs/superpowers/specs/2026-10-16-forms-step3-personas.md`.

## Review Focus

These are five conditions the spec implies but §8.5 doesn't name, most likely first. Each has its test in the owning task.

1. **A debt answered "secured" and then changed to No keeps its stored link.** It must never print on J, count in a total, or cover a legacy figure. Tests: Task 1, `test_a_debt_no_longer_secured_never_reaches_schedule_j`, and its case in the shared table.
2. **A vehicle lease changed to another kind keeps its vehicle and payment** (3c3 keeps them). It must never print. Test: Task 1, `test_a_lease_changed_away_from_a_vehicle_never_reaches_schedule_j`.
3. **The car is removed on Assets.** The link goes null (`SET_NULL`), the payment leaves J 17 and every total at once, and a legacy figure it covered shows its gap again. Test: Task 4, `test_removing_the_car_brings_back_the_legacy_gap`.
4. **Two loans on one car.** They share its line and add, rather than taking 17a and 17b. Test: Task 1, `test_two_loans_on_one_car_add_on_its_line`.
5. **A client sends a legacy figure other than 0.** A figure is dropped, never stored, and `legacy_payments` reads as before. A value no expense amount could take is a 400 (R6). Test: Task 4, `test_a_legacy_figure_takes_only_zero`.

## Rulings

These settle what the spec leaves open, correct what the code contradicts, and name what each costs if wrong. `rulings` in a task means this section.

- **R1. `linked_payments(session) -> LinkedPayments` in `claims.py`.** The module imports no model and reads relations by attribute, as `claim_step_gaps` does.
  - **A debt counts** when it is confirmed (`session.debts.confirmed()`; drafts never print, §8.1), `is_secured` is True, and `secured_by` is live (`link_is_live`).
    - A debt answered No to "Can the lender take back property…" keeps its stored link but never counts: 3c3 keeps stale answers, and the filer said it isn't secured.
    - Cost if wrong: a stale payment prints.
  - **A lease counts** when `contract_type == "lease"`, `lease_kind == "vehicle"` and `vehicle_asset` is live (the 3c3 hand-off). The relation is `session.executory_contracts`.
  - `monthly_payment` None counts as $0. A claim gap names it.
  - **Home row:** an A/B row on line 1 or line 4 whose `details.lives_here == "yes"`.
    - A debt on it goes to J 5 when `home_payment_line == "additional"`, and to J 4 otherwise. Otherwise means "first", or null, which is a claim gap.
    - A vehicle lease on a home row goes to J 4, as rent for the residence.
    - `home_payment_line` is read on a home row only (the 3c3 hand-off).
  - **J 20a:** a line 1 row not answered "yes". That is No, or null, which is a claim gap.
  - **Two unanswered cases depart from §8.1 and §12.** §8.1's table matches only "answered No" (20a) and "first" (J 4), so under it a null `lives_here` or a null `home_payment_line` would fall to "any other property" (17c). §12 compares `other_property_mortgages` with line 1 rows "answered No".
    - Here a null `lives_here` on line 1 counts as 20a, and in that comparison. A null `home_payment_line` on a home row counts as J 4, and raises the line 4 question.
    - Why: both sit behind a claim gap (the Assets "Do you live here?" gap, and `DEBT_GAP_HOME_LINE`) that refuses Complete and the forms first, so neither ever prints. Reading them as the likelier answer keeps a payment from jumping between 17c and 20a, or J 4, as the filer answers.
    - Cost if wrong: before the filer answers "Do you live here?", a link on that row can cover a stored `other_property_mortgages`, so the legacy gap shows only after the answer.
  - **Vehicle rows:** line 3 rows, then line 4 rows, in `ordered_assets` order, leaving out a lived-in line 4 row.
    - 17a is vehicle 1, 17b vehicle 2, 17c vehicle 3 and 17d vehicle 4, by position: B19's "nth A/B vehicle row", and B45's four words.
    - A vehicle with no counted payment leaves its line blank.
  - **Other property:** any other asset with at least one counted debt, in `ordered_assets` order. Payments on one asset add (B45's shared slot). A vehicle lease linked to a row that is neither a home row nor a vehicle row (no picker offers one) counts there too, so every counted payment prints somewhere.
  - **17c and 17d** take entries in this order: vehicle 3, vehicle 4, vehicles 5 and later, then each other-property asset.
    - 17c takes the first entry and 17d the second. Every later entry adds into 17d.
    - Each line prints above $0 only.
  - **The Specify words** print beside a printed amount only. They are one of four strings:
    - `"Vehicle 3"` or `"Vehicle 4"`, for a vehicle in its own slot;
    - `"Payment on other property"`, for one other-property asset in its own slot;
    - `"Other secured payments"`, on 17d, when the entries after the second add up to more than $0.
  - Cost of the positional reading if wrong: an other-property payment lands on 17d while a vehicle 3 with no payment leaves 17c blank.
