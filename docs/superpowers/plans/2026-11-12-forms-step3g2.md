# Forms step 3g2, exemptions: print: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Schedule C prints the filer's exemption answers that 3g1 stores: line 1, every claim (its item's description, Schedule A/B line and value, the amount tick, the amount and the law) on 15 slots and copies of page 2 from row 16, page numbers, and lines 3 and 3-1; the old `2.2` binding goes.

**Architecture:**

- **One reader, one namespace.** `exemption_rows(session)` (in `apps/forms/services/exemption_items.py`, beside 3g1's `exemption_items`) turns the session's claims into the rows Schedule C prints, each cell already a string, read once per resolve. A new binding namespace, `exemptions.`, reads them: `exemptions.claims[].<attr>` through `EXEMPTION_CELLS`, and `exemptions.line_1|line_3|line_3_1` as scalars. Every refusal of an `exemptions.` box links to `/exemptions`.
- **A tool writes the schema.** `data/forms/field_index/tools/build_schedule_c.py` writes `schedule_c.json` (group `c_part_2`, 15 slots, `extra_page: 2`, page numbers) and Schedule C's rows in `step2_verification.json`, as the claims and List of Creditors tools do (B9).
- **Placement is proven from the template's own labels**, never from the tool's table: tier 2's addendum rows assert whatever box the tool chose, so they can't catch a misplaced box.
- No migration, no seed, no frontend change. 3g1 already asks, stores and seeds every answer.

**Tech Stack:** Django 5.0, pypdf/PyMuPDF form engine, pytest-django with sqlite. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-12-forms-step3g-design.md` §6 (cited `§6.x`), with §8's and §9's 3g2 items and §11's calls B9, B10, B12, B13 and B16. 3g1's plan (`docs/superpowers/plans/2026-11-12-forms-step3g1.md`) holds rulings this plan keeps, cited `3g1 Pn`. ## Global Constraints

- **Nothing prints that the filer didn't give.** A law, an amount, a tick on line 1, 3 or 3-1, or an amount box prints only from the filer's own answer. Every `exemptions.` binding is `source: "asked"` and `legal_review: true`. The description, line and value are copied from the item's Schedule A/B row, never typed (§1 goals).
- **Blank, not 0.00.** An item value A/B prints blank prints blank; a "100% of fair market value" claim prints no amount; a $0 dollar claim prints "0.00"; a $0 item value prints "0.00" (§6.3). Money prints as `money_or_blank` does ("6500.00", no comma).
- **Schedule C's boxes print what Schedule A/B prints.** The line label and value come from 3g1's `exemption_items` (B13, B16), so the two forms can't drift.

## Review Focus

Five conditions a filer will meet that §6.5 doesn't spell out, most likely first. Each has its test in the owning task.

1. **A claim on a line 28 or 29 row** (a tax refund, support owed to the filer). A/B prints those lines as sums by kind, with no box of the row's own, so Schedule C prints the bare line ("28") and no value (3g1 P7). Test: Task 1, `test_a_tax_refund_claim_prints_its_line_and_no_value`.
2. **An item on a sheet-numbered line** (a second household-goods row prints "6.2"). Schedule C prints A/B's sheet number in its narrow line box. Tests: Task 3's rows and copies tests, built on line 6 rows labelled "6", "6.2", … "6.28".
3. **A short description left stored after the item was renamed** to a name that fits. The page hides the box and the gate passes; Schedule C prints the item's name, not the old words (R4). Test: Task 1, `test_a_short_description_prints_only_while_the_items_name_does_not_fit`.
4. **Accounts saved out of A/B's kind order** (a savings account before a checking account). Claims print in their items' saved order, so 17.3 can print above 17.1, as the page lists them (R3). Test: Task 1, `test_claims_follow_their_items_saved_order_across_kinds_of_one_line`.
5. **Line 3 Yes, and a 3-1 answer stored under No.** 3-1 prints only under Yes; a value stored under No prints nothing. Also a $0 claim and a $0 item value print "0.00". Tests: Task 1, `test_line_3_1_prints_only_under_line_3_yes`, `test_a_zero_dollar_claim_and_a_zero_value_print_0_00`.

## Rulings

These settle what the spec leaves open or the code contradicts, and name what each costs if wrong. `rulings` in a task means this section.

- **R1. A namespace, not rules.** `exemptions.claims[].<attr>` (rows) and `exemptions.line_1`, `exemptions.line_3`, `exemptions.line_3_1` (scalars, the engine's first since `sofa.<attr>`: `resolve_binding` returns a `str` for them, since a list on a non-repeat field prints nothing, `fill_resolver.py:522-523`). - **R2. One reader, read once a resolve, imported inside functions.** `exemption_rows(session)` builds every printed row from one claims query, one `exemption_items(session)` and at most one catalog read; all six cells read the same list, so a filtered row can never shift one column against another. `resolve_binding` resolves each slot field on its own (`fill_resolver.py:926`: 90 calls a Schedule C), so the rows are held in a `ContextVar` under `one_read_of_exemptions()`, which `resolve_parts` enters beside `one_read_of_assets()` and `one_read_of_claims()` (the `claim_rows` pattern, `claim_rows.py:89-110, 197-205`). - **R3. Which claims print, in what order.** Only a claim whose item is live (its `asset_id` is an `ExemptionItem.id` of this session) prints; the gate refuses any other first, but `resolve_parts` also runs ungated (tests, the oracle), so the reader drops them itself (§6.5: "a claim with no live item never prints").
